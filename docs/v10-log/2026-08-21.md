# 2026-08-21 — rung 10: reading the disk, and the shell that was never there

K15 closed rung 8's host half yesterday. Rung 10 — a shippable `v10.disk` —
had one open question recorded in the plan: *"the real open question is where
the staged root comes from"*, K10.3 installing into `/usr/w10` on one image
chain while K14 builds disks on another.

That question dissolved in a minute and a much worse one took its place. Every
measurement below is host-side; **no simulator ran until the source-disk
rebuild at the end**.

---

## 1. The sequencing question was not a question

`.k13` is `stage1.k102.k7.k13` — it **descends from `.k102`**, so the
disk-building machine already carries K10.2's 26 archives, which is K10.3's
only precondition. Confirmed by reading the image rather than by booting it:
`/usr/lib` holds all 26 plus `yaccpar`, and `/usr/s1` holds stage 1's complete
toolchain. So K10.3 runs on the `.k13` chain and one machine carries
everything.

The tempting shortcut was to extract `/usr/w10` from the existing `.k103`
image host-side, serve it over netfs and let K14 copy it in — saving a
40-minute relink and losing nothing in provenance, since `.k103` and `.k13`
share the same `.k102` ancestor. **Rejected**, and the reason is worth
keeping: that would put the new reader in the *build* path as well as the
*verification* path, so a bug in it would write and then bless the same wrong
bytes. Circular verification is the failure this project keeps cataloguing
(*"two readings agreeing is not two readings being right"*). The reader stays
an instrument.

## 2. `tools/v10fs.py` — and it is proven, not reviewed

`v8fs.py` for the Tenth Edition. Its argument applies twice over here,
because a V10 guest is a poor witness about its own filesystem: `ls` exits 0
for a file that does not exist, and a full filesystem **sleeps** rather than
failing.

The trap the file exists to get right is that **a block address has two
encodings**. The inode packs 13 addresses at three bytes each — `l3tol`, whose
**vax** arm is three bytes little-endian with a zero high byte, where the
pdp11 arm of the same file packs the identical bytes in a different order —
while the indirect blocks hold full 4-byte `daddr_t`, because `bmap()` reads
them as `b_un.b_daddr` sized `BSIZE/sizeof(daddr_t)` = 1024.

Every constant is quoted from the tape: `lsys/sys/ino.h` (64-byte dinode),
`lsys/sys/dir.h` (DIRSIZ 14, 16 bytes), `NADDR` 13 (`lsys/sys/inode.h:12`),
`itod`/`itoo` (`param.h:86`), `fsbtodb = b*8` (`param.h:88`).

**The proof is nine binaries extracted from the golden and byte-identical to
the tape's own prebuilt copies:**

	sh  ls  ps  make  sed  diff  pr  test  as

`as` is 57,203 bytes — fourteen blocks — so it goes through the single
indirect. That cannot come out right unless `itod`, `itoo`, the `l3tol` arm,
the 3-vs-4-byte split, `NADDR`, `NSHIFT` and `NMASK` are all correct at once.
It is a much stronger check than the block accounting that preceded it: block
counts can agree while a constant is subtly wrong, because an off-by-one in
`itoo` still yields *a* 64-byte inode.

Block accounting agrees anyway, to within four blocks of 516 and two of 1547,
the residue being what `mkbitfs` marks rather than what this reads.

### The `prov` verb, and both of its false readings

`prov` splits a disk's files into the tape's bytes and ours. Both faults ran
in the **flattering** direction, which is the sort that survives review.

**An empty file is not evidence of anything.** `/etc/mtab` and `/etc/utmp` are
zero bytes, every empty file has the same sha256, and the tape happens to
carry one (`blit/demo/mpx/.jciferr`) — so the oracle credited Bell Labs with
two files this project had truncated.

**And an archive identical in every member read as foreign.** The golden's
`/lib/libc.a` differs from the tape's in exactly **ten bytes**, all of them
the `__.SYMDEF` member's ar-header timestamp:

	tape   743340498     (mid-1993)
	disk  1786908310     (August 2026)

because CLAUDE.md requires re-`ranlib`ing an archive at its destination — `cp`
bumps the mtime and that alone demotes a good archive to V10 `ld`'s
single-pass case 3. **The re-ranlib is correct and the whole-file hash called
the correct thing foreign.** Archives are now fingerprinted per member with
`__.SYMDEF` dropped, which is stage 2's own per-member-witness discipline.

### First findings, none of which needed a boot

	base golden      /unix = lsys/astro/seki.u    Bell Labs', for another machine
	.k7 and later    /unix = 228,310 bytes        ours, from ipnx780.m
	K14's built disk root 61 files / 2.1 MB      complete boot path
	                 /usr  1 directory, 0 files  EMPTY

`/unix`'s `addr[]` on the built disk is **ten direct plus one indirect**, which
is `lsys/boot/README`'s *"no more than singly indirect"* satisfied to the
letter.

## 3. `sh` was specified into `/usr/bin`, and `/usr` is a separate filesystem

This is the day's real finding, and it would have produced a disk that boots
and then stops.

	world.link:231    sh /usr/bin default -

`default` means *"ours, because it had to go somewhere"*. `where.txt` had **no
row for `sh` at all**, because `commands()` asked *"does `cmd/X` hold `X.c`"*
and `cmd/sh`'s main is `main.c` — the same blind spot the `MK` comment already
recorded for the toolchain, silently dropping **92 units**.

Why it matters, measured rather than reasoned. Strings out of the golden's own
`/etc/init`:

	/bin/sh   /etc/getty   /etc/rc   /etc/ttys   /etc/utmp   /usr/adm/wtmp

and `/etc/rc` entire:

	PATH=/bin:/etc:/usr/bin
	export PATH
	/etc/mount /dev/ra0c /usr
	cat /etc/motd

So `init` execs `/bin/sh`, and the shell it execs is what runs the script that
mounts `/usr`. A shell only in `/usr/bin` **does not exist at the moment it is
needed** — V8 stage 8's disk that *"walked 4,507 files and then stopped dead
after autoconfig with the CPU idle"*, on the Tenth Edition.

### The fix is to read what the tape already says

`where.txt` carried five hand-transcribed install rules and inferred the rest.
`mk_paths()` now scans each unit's own makefile for `cp <name> <dir>` and finds
**43**.

	10 commands MOVED to the directory the tape names
	   sh make tp kasb -> /bin       config dump -> /etc
	   diff3 apsend style -> /usr/lib     map -> /usr/maps
	30 more kept their directory and gained real evidence (22 mkfile, 8 v8)
	where.txt 266 -> 347 rows

Two of the moves look odd and are historically right: `diff3` belongs in
`/usr/lib` because `diff -3` invokes it, and `map` really is installed to
`/usr/maps`.

**The source token must be the product's own name**, which is what separates an
install from a backup. `cmd/sh/makefile:37` is three commands on one line:

	mv /bin/sh /bin/osh;	cp sh /bin/sh;	strip /bin/sh

The **first** would answer `/bin/osh` to a scanner reading destinations.
Matching `cp sh …` gets it right and rejects `cp $(FILES) /usr/src/cmd/make`
at the same time. Continuation lines joined first, recipes split on `;` — both
of them rules this project already had.

### And a second list said otherwise

`prebuilt.txt` hardcoded `TOOLCHAIN = {as, ranlib, lex, make, sh, sed}` to fill
that very hole. The scan agrees with five and **contradicts the sixth**: it
said `sed → /bin` where the tape (`cp sed /usr/bin`) and V8's measured disk
both say `/usr/bin`. So the hardcoded value was simply wrong. `sed` is removed
with its reasons recorded, the five that agree stay as a **live control**, and
both generators now halt on a disagreement.

Both guards were proved to bite before being trusted — claiming `as` lives in
`/usr/bin` stops `v10-where.py`, claiming `make` does stops `v10-prebuilt.py`
— which is the only reason a useless guard ever gets found.

**A note on circularity, checked before relying on it.** The first idea was to
add a `gold` source: measure install paths on V10's own disk. That is
**circular** — `prebuilt.txt` uses the same authority scheme (`man`, `v8`,
`toolchain`, `default`) and 30 of its 57 rows are `default`, so the golden's
layout *is* our earlier inference read back. Dropped.

## 4. What a shipped disk carries — decided on measurement

The instinct is to keep Bell Labs' binary wherever one exists. CLAUDE.md rules
that out in its own words: the 46 prebuilt commands are *"developers' working
directories, so what survived is whatever was last compiled in place"*, and
they are *"an ORACLE, not a shortcut … use the 46 to check what we build, never
to skip building it"*. Build detritus is not a specification; the **source**
is, and K10.3's 203 commands were built from it by V10's own compiler. Stage 2
settled the identical question the identical way.

So: **our build where we have one, the tape's where we do not.** The 40
prebuilt commands we cannot build — `2500 adb bcp picasso lcc lex …` — keep
Bell Labs' bytes untouched, because nothing overlays them.

How much the choice actually decides, measured:

	K10.3 staged                       203 files, 6.5 MB
	  collide with a builder path       50
	  new                              153
	of the 50 collisions
	  Bell Labs' own bytes              19
	  ours already                      31
	sampled collisions, text+data identical    9 of 10

So the build is **deterministic in generated code** — the differences are
twelve bytes of symbol table, one entry, the source path — and "which build
wins" is a real question for almost none of them. The exception is
`/etc/login`, genuinely smaller in K10.3's build (text 22528 → 20480), which is
the documented Share-scheduler removal.

**And it is safe to overlay, which was checked and not assumed.** V10's `ld`
writes its output even when symbols are undefined; it reports them and
**clears the execute bits**. All 203 staged files carry `x`, so `ld` resolved
every symbol in every one.

The driver reads the finished image's **contents** rather than only its

## 6. Two process faults, both mine, both cheap

**`"$IMG:c"` in zsh silently drops the `:c`.** `$K:c` is a history modifier, so
the argument arrives with no partition, defaults to root, and the tool
truthfully reports that `/bin/lex` is not there. **Nine files read as MISSING
when all nine existed.** An RA81 image holds two filesystems, so this is K11's
*"a guest can report success about the wrong disk"* moved to the host.
`${K}:c` is the fix in the shell; `v10fs.py` now prints the filesystem it read
on stderr every time, because a banner is the only thing that makes the wrong
answer visible instead of plausible.

**`nohup … &` inside a backgrounded call reported "exit 0" over a run that was
still booting.** The ampersand makes the wrapping shell exit immediately, so
completion was announced while `vax780`, `expect` and the driver were all
alive — and the log at that moment stopped mid-`attach il nat:`, which looks
exactly like the documented SLiRP bind failure. **Nothing was damaged, and
only not starting the next run on top of it kept that true.** Checked for a
live simulator before doing anything else; found one; waited.

Also caught by checking rather than by reading a summary: `v10-world.py` needs
`--write`, and a bare run prints its survey and writes nothing. I nearly
recorded "0 rows moved" as a result about the fix. `git diff` being empty is
what caught it.

## 7. The simulator is a property of the image, and K10.3 hardcoded it

The first attempt to run K10.3 on the `.k13` chain panicked in the boot:

	unix
	type 2 sp x7fffec00 code x0 pc x800139f8 ...  panic: trap
	type 8 sp x7fffec00 code x0 pc x80009581 ...  panic again: trap
	HALT instruction, PC: 80000BB3 (HALT)

`v10-link.exp` spawns **vax750**, because K10.3 was written for the `.k102`
chain. The `.k13` chain's `/unix` is our own `ipnx780` kernel, which dies on a
750 for hardware that is not there — `ms780`, `dw780`, `mba`. Two separate
faults, fixed separately.

**The harness took eight minutes to say so, and then said the wrong thing.**
`v10_must "ogin" 480` reported *"never saw 'ogin' after 480s"* — the symptom.
The diagnosis came from reading the transcript by hand.

**`v10_select_machine` asks the kernel.** K7's kernel carries its own banner
string, `Unix 10e ipnx 780`, which is the line K9's transcript prints on the
console; `lsys/astro/seki.u` does not. `tools/v10fs.py` reads it off the image
host-side, with no simulator, and the simulator follows. That is a measurement
of the artefact rather than a convention about its filename — the same reason
provenance here comes from hashes and never from grepping a binary for
`vaxpcc2`.

	golden                 no ipnx780 banner  ->  vax750 + uda750
	.stage1.k102.k7.k13    ipnx780 banner     ->  vax780 + uda (star)

**`v10_must_boot` makes a panic a first-class outcome**, so the next one fails
in seconds naming the likely cause. Two expect traps avoided deliberately, both
already recorded in CLAUDE.md: **no `--`**, because it ends option processing
and would silently turn a later `-re` into a literal glob; and the **flat**
form, the only one of expect's three spellings that both honours `-timeout` and
re-splits into pattern/action pairs.

Proved against real processes rather than under the dry-run's stubs, because the
success path is the one that would break every harness:

	prints `login: '      -> matches, boot proceeds          exit 0
	prints `panic: trap'  -> bails at once, names the cause   exit 7
	prints nothing        -> bails at the timeout, 3s         exit 7

The third is not redundant: it confirms `-timeout` is still honoured with four
pattern pairs.

**Nothing was at risk while this was found, and that was the clone rule rather
than luck.** Both attached images were clones; `.k13` itself still reads its
original mtime. The orphan check showed the simulator idle at `sim>` — 0.0% CPU,
state `Ss+`, parent alive — rather than spinning, and the harness reaped itself
and reported the clone as damaged:

	V10-BAIL: never saw 'ogin' after 480s
	V10-BAIL: guest stopped at sim> and quit -- NOT cleanly halted,
	V10-BAIL: so treat this image as damaged until a hash says otherwise.

## 8. `$var:` followed by a letter, twice in one hour

The zsh modifier trap from §6 recurred as **`:a`** — the absolute-path modifier
— in a loop over image names, so every read returned nothing and it looked like
an empty kernel rather than a wrong path. The call said `2>/dev/null`, which
also suppressed the banner added an hour earlier to catch exactly this.

zsh's modifiers are a family (`:h :t :r :e :a :A :c :l :u :s`), so **any**
`$var:` followed by a letter is a hazard. Always `${var}:part`. And a banner on
stderr does not help a call that discards stderr.

## 10. `sh$` does not match `sh\r`, and the report said so out loud

The run printed

	sh did NOT build, and it is the generic recipe's limit rather than
	a fact about the tape ...

three lines from a log containing `CLINKED sh`, over a staged root holding a
57,494-byte `/w10/bin/sh`. The test was

	if ! grep -qE 'CLINKED sh$' "$LOG"

and `CLINKED` is echoed by the **guest**, so it arrives through the tty as
`CLINKED sh\r\n` — and BSD grep's `$` anchors *after* the carriage return. The
test was permanently true. The anchor cannot simply be dropped: unanchored,
`CLINKED sh` also matches `CLINKED showq`. `[[:space:]]*$` keeps the anchor and
tolerates the `\r`.

**The distinction that matters, checked rather than assumed.** Four sibling
harnesses anchor on `$` over the same logs and every one is correct, because they
match lines *expect* printed with `puts` — `\n` only. This was the only one
matching a line the guest printed. Measured on the real logs, anchored count
against count-after-`tr -d '\r'`:

	v10-link.sh    CLINKED sh$          0  vs  1   <-- broken
	v10-mux.sh     the oracle.*ok$      2  vs  2
	v10-stage2.sh  NO$                  0  vs  0
	v10-stage3.sh  FIXPOINT.*ok$        7  vs  7
	v10-stage3.sh  FIXPOINT.*NO$        0  vs  0

So one site is fixed rather than five changed blindly. **Anchor freely on our own
output; never on the guest's without allowing for the `\r`.**

It hid twice over. A permanently-true test stops being read — the same mechanism
that let `atof` hide in stage 2. And checking the pattern by hand **confirmed the
opposite**, because this shell's `grep` is a ugrep shim that treats `\r\n` as the
line terminator, while the harness runs BSD grep under `bash`. *Test with the
tool that runs.*

### What netfs cost, measured in passing

The `mkbitfs` build spent eleven minutes on one `make`, and sampling netfsd's own

it bounds every V10 harness. The simulator sat at 100% CPU throughout, which
carries no information: the V10 config sets no `set cpu idle`, so it burns a core
either way.

## 12. #13 advanced: the server is excluded, and the number is 9.46 s IN THE GUEST

The netfsd instrument built on 2026-08-20 paid off on its first real workload.
Three connections from K14's run:

	/n/tree  122 requests   serving 102.8 ms total, 0.84 ms mean, 10.0 ms worst
	                        waiting on the guest 1154.0 s
	/n/mk      7 requests   serving   2.5 ms total, 0.36 ms mean
	/n/ours    1 request    serving   0.0 ms

**0.84 ms of server work against 9.46 s per request of waiting on the guest — a
factor of eleven thousand.** Together with the card's own counters from the same
run,

	packets received 560   packets sent 613
	receive errors     0   transmit errors 0
	Read Queue Loss    0   High 3

this excludes, in one measurement: the server, the wire, dropped frames, and the
queue. 560 received over 122 requests is 4.6 frames per request, which a
4096-byte reply explains on its own — three data frames plus ACKs — so the packet
counts are not evidence of retransmission either. The 53-frame send surplus is
8.6%, and ARP, the self-loopback and four connection setups account for that
order.

**And the magnitude constrains the diagnosis.** 9.46 s cannot be assembled from
10 ms clock ticks, so the leading candidate recorded in CLAUDE.md —
`ilrcvbufs()` posting one receive buffer per command, three command round trips
per frame — is off by two orders of magnitude even if it is real. Something in
the guest waits on a **seconds-scale** timer.

Host-side, every sleep on the V10 receive path was read and none of them is it:

	ni1010a.c:167,188,233   tsleep(..., 5)   FIVE SECONDS, but init only
	                        (ILC_RESET / ILC_STAT / ILC_ONLINE)
	streamio.c:196          tsleep(..., 1)   stclose() -- the CLOSE path, up
	                        to 60 one-second sleeps draining a queue
	streamio.c:314,501      tsleep(..., 30)  timeouts, not delays: they fire
	                        only when data does NOT arrive
	neta.c:630              sleep(..., PZERO) untimed

`streamio.c:196` is worth keeping for its own sake — **closing a stream can take
up to sixty seconds** — but it is not on the per-request path.

So #13 is now a much narrower question than "netfs is slow": *what does the guest
wait on for 9.46 seconds between one reply and the next request?* The remaining
instrument is the one already built and still unused —
`V10_IL_TRACE=work/il.trace bash tools/v10-netread.sh` — which timestamps every
frame and can therefore say whether the time goes before our reply reaches the
guest or after. Anything else is speculation, and this file has enough of that in
its history.

**Before changing `pdp11_il.c`, re-run `tools/net-selftest.sh` against V8**: its
290 s → 11 s is measured and must not regress to fix V10.

## 13. The duplicates: a removal pass designed, computed, and rejected

The shipped disk carries four executables at two paths, and the temptation was
to delete the stale copy. The rule would be *"remove a copied file whose name
our tables place elsewhere"*. Computed, it matched **forty paths** — almost all
of them build scratch K14 never copies (`/usr/obj`, `/usr/s1`, `/usr/k13obj`,
`/tmp/ct`). My own sanity assertion caught it: I had asserted `sleep` must not
appear, and it did.

Restricted to what K14 actually copies, it matches three:

	diff3    golden /usr/bin/diff3    ours /usr/lib/diff3   (table says /usr/lib)
	sed      golden /bin/sed          ours /usr/bin/sed     (table says /usr/bin)
	sleep    golden /bin/sleep        ours /usr/bin/sleep   (table says /usr/bin)

**And one of those must not be touched.** Removing `/bin/sleep` leaves `sleep`
only under `/usr`, which `/etc/rc` mounts — so it would not exist in
**single-user mode**. V10's kernel does not sync on halt (`lsys/md/machdep.c`'s
`boot()` is two lines and `RB_NOSYNC` is referenced nowhere), which makes the
userland `sync; sleep; sync` the entire flush. Deleting a binary from a shipped
disk to tidy a path is not worth risking a safe shutdown.

`sed` is the one with a real argument for removal — `PATH=/bin:/etc:/usr/bin`, so
the tape's `/bin/sed` **shadows** ours, which contradicts the stated content
decision. But it is one command, both copies work, and the cause is upstream: the
golden was built under the older `prebuilt.txt`. **The fix belongs at the cause.**

What was done instead costs nothing and removes the unknown: the host-side check
now **reports every duplicate on every build**.

	executables at more than one path (4) -- reported, not removed:
	  diff3     /usr/bin/diff3 (12288)  /usr/lib/diff3 (34988)
	  ld        /bin/ld (38674)  /lib/ld (38674)
	  sed       /bin/sed (40143)  /usr/bin/sed (44182)
	  sleep     /bin/sleep (29413)  /usr/bin/sleep (29415)

A duplicate every build names is a known property. One that needs an ad-hoc audit
to find is not.

## 14. The app: the machine is data, and V10's values are written down

`Machine` had `v8` hardcoded in eight places. `MachineSpec` now holds them once,
with `.v8` and `.v10`, and two mistakes the port would have made are explicit:

**`resumeCpu` is not `cpu`.** V8 must *re-issue* its idle pattern after
`restore`, because `UNIT_IDLE` survives a save/restore while `cpu_idle_mask` does
not. V10 must *not* re-issue `set cpu 8m` — sizing memory after `restore` writes
over the state just restored. A bug that would only appear on the second launch.

**`preDevices` exists because order is not cosmetic.** V10's proven sequence
enables the DZ *before* configuring it, and setting a line count on a disabled
device is not something to rely on. V8's list is empty rather than newly
populated: a refactor that changes what the working machine emits is not a
refactor.

And V10 carries **no `set cpu idle` at all**, recorded as a known gap: V8's
`idle=4.1BSD` matches its kernel because that kernel is 4.1BSD-derived and V10's
is not, and no V10 harness has ever set one — measured 43:20 of CPU in 44:24
elapsed. Harmless on a desktop, not harmless on an iPad battery.

Proved equivalent for V8 at every level, because a refactor of the shipping
machine has to be:

	both emitted configs byte-identical, compared line by line
	  against the original templates rather than by eye
	the bundle lookups resolve to the SAME FILES, checked against the
	  real built bundle -- forResource:"v8.disk" withExtension:nil is
	  the same URL as forResource:"v8" withExtension:"disk"
	both targets build; tools/app-check.sh --full PASSES

The gate proved it bites in passing: the first build went to the default
DerivedData and `app-check` failed *naming `Machine.swift`* — better evidence than
a synthetic `touch`.

Still not wired into the UI. A second machine also needs a second `Machine`, its
own windows and its own shares, plus a decision that is not mine: a second
committed image would be a **second** exception to the no-binaries rule, whose
sole current member is `image/ipnx-v8-rp07.img.xz`.

## 15. V10 is in the app bundle, and the blocker I named was wrong

I recorded that carrying V10 in the app needed a decision — a second committed
binary, a second exception to the no-binaries rule. **That was wrong, and
correcting it is what unblocked the work.** The embed phase reads `v8.disk` out
of `work/myv8/rp07new`, not out of git; `image/ipnx-v8-rp07.img.xz` is committed
for an unrelated reason, because stage 8 lifts `v8/mk/gen/carry.txt` off it and
it is therefore an *input to the next build* rather than the app's media. V10 has
no such build-chain role. No decision was needed and none was taken.

So the existing `Embed V8 media` phase now embeds both, in both targets:

	embedded v8.disk + bootV8 (image 8ccbf05614e8)
	embedded v10.disk + uda   (image 69e739aa58f7)

`uda` is the tape's own boot ROM, `lsys/boot/star/uda`, byte-identical in the
bundle. `v10.disk.id` is the same identity stamp for the same reason: a working
copy diverges the moment the guest writes, so only a record of *which* image it
was cut from can spot a stale one. Absent media is a warning, not an error — a
fresh checkout has no `work/`.

`tools/app-check.sh` now asserts the V10 chain, and **both new gates were proved
to bite**: a stale `v10.disk.id` and a missing boot ROM each fail by name, and
restoring them returns to PASS. An unchecked second machine goes stale exactly as
invisibly as V8 did, which is the whole reason that script exists.

## 16. `idle=4.1BSD` WORKS ON V10 — 99.8% of a core to 1.7%

Predicted first, from two primary sources and no simulator. SIMH's 4.1BSD-family
detection (`VAX_IDLE_ULT1X`, `vax_cpu.c:2579`) fires on an `FFS` that finds no
set bits, **at IPL 0**, **in system space**, **below virtual 0x3000**. And:

	V8  usr/sys/sys/locore.s:705-708
	V10 lsys/ml/swtch.s:82-85          -- diffed: IDENTICAL

	sw1:	ffs	$0,$32,_whichqs,r0	# look for non-empty queue
		bneq	sw1a
		mtpr	$0,$IPL			# must allow interrupts here
		brw	sw1			# this is an idle loop!

The address was the only open condition, and the built kernel's own symbol table
answers it: **`sw1` at 0x80001136**, low `0x1136` = 4,406, inside the 12,288-byte
window. All five conditions hold.

Then `tools/v10-idle.sh` asked the machine — A/B on one disk, one variable:

	idle off   99.8% of a core over 30s   (cpu 5.66 -> 35.60)
	idle on     1.7% of a core over 30s   (cpu 0.70 ->  1.20)

**Better than V8's 2.7%.** Measured as a **duty cycle** from cumulative cpu-time
deltas rather than `ps -o %cpu`, which on macOS is a decaying average that a
single reading cannot interpret. And the guest's clock still reads correctly
afterwards (`Fri Aug 21 15:38:01 EST 2026`) — an idle that slept through timer
interrupts would be worse than none, which is the check V8's own idle patch had
to pass before it was accepted.

Both arms halted cleanly (`death`, then the IPL-31 spin at `BRB 80015CC9`) and
both ran on clones: the built disk still hashes `69e739aa58f7`, matching the
bundle stamp.

**An incidental confirmation, from the run that failed on a missing
`v10_login`:** SIMH stopped the machine at `PC: 8000113F (BNEQ 80001147)` — that
is `bneq sw1a` at `sw1+9`. The machine really was sitting in the loop the symbol
table had located.

The setting is now in `MachineSpec.v10`, and it is exactly what `resumeCpu` was
built for: the idle pattern must be re-issued after `restore` because
`cpu_idle_mask` is not saved, while `set cpu 8m` must not be, because sizing
memory after a restore writes over what was just restored.

## 18. The app boots the Tenth Edition — and launching it found a real defect

Scoped to **one machine at a time**, deliberately. Two simultaneous machines
needs a second `Machine`, `Terminal5620`, `SessionStore` and pair of
`FileShare`s — all `@StateObject` singletons in `IpnxApp` today — plus a window
key carrying which machine, and the DMD half of that cannot be verified without
a human at a mouse. One at a time keeps every singleton a singleton, and it is
the actual feature.

`MachineSpec.current` reads the preference and **falls back rather than
failing**: a stored choice can outlive the media it names, and booting what is
there beats refusing to boot. The picker offers only `MachineSpec.available`, so
an edition the bundle cannot provision is never offered — otherwise a missing
file becomes a launch that throws `mediaMissing` with nothing to say why.

### Verified by launching, not by reading the diff

**V8, unchanged.** The app rewrote `boot.conf` with the *same* line numbering
(`-16` is `at rp0 v8.disk`, `-19` is `attach il nat:`), re-provisioned because
the image stamp had moved, and `tty07` answered:

	ipnx-v8
	login:

with mark parity exactly as documented — 21 of 35 bytes high-bit set. Quit
cleanly with a 1.9 MB snapshot.

**V10.** Provisioned `~/Library/Application Support/ipnx/v10` with the 456 MB
disk, the tape's boot ROM and an identity stamp, and wrote a config ending

	set rq0 ra81 / attach rq0 v10.disk / load -o uda FA00
	dep sp 200 / dep r1 0 / dep r3 0 / dep r5 0 / run FA02

It booted, and it **idled: 13.6% of a core for the whole app**, which is the dmd
thread plus a SIMH no longer burning one — so the idle finding of §16 holds in
the shipping path and not only in a harness. Quit cleanly with a 1.76 MB
snapshot, so save/restore works for the second machine too.

### The defect only a launch could find

**No tty answered.** The golden's `/etc/ttys` ships all eight gettys *disabled*:

	12console            <- column 1 is the on/off flag
	02tty00 ... 02tty07  <- `0': no getty

so V10 in the app came up with a login prompt on the **console** — which is
read-only behind a lock there — and eight dead terminal windows. Nothing in the
build, the config, the boot or `app-check` could have shown this; only dialling a
line did.

K14 now enables them, and the host-side check asserts the **shipped** file rather
than only the guest's `grep`. Proved to bite against the disk that already
existed: *"/etc/ttys enables 0 gettys, not 8 — a machine with no terminal"*.

**Not an authenticity question.** `/etc/ttys` is configuration — how many
terminals *this* machine has — and V8's golden has its gettys on for the same
reason. The tape does not dictate a site's terminal count. Supported by the disk
as built: all eight `/dev/tty0N` nodes exist and `ipnx780.m` carries one `dz11`,
which SIMH gives eight lines.

### One self-inflicted hazard, caught by the gate it exists for

Rebuilding the app *while K14 was writing* `ipnx-v10-made.img` embedded a
partially-written disk. Harmless to K14 — a read cannot corrupt a write — and
`app-check --full` named it immediately:

	v10.disk.id does not match work/v10gold/ipnx-v10-made.img

which is precisely the failure that check was added for, catching its author.

## 19. `/usr` came up empty in the app, and the halt marker was why

The Tenth Edition booted in the app, idled, answered on eight ttys — and had an
**empty `/usr`**. The app's own console said why:

	unix
	Unix 10e ipnx 780
	mem = 6062080
	mount /dev/ra0c on /usr type 0: In use

Reproducible on a completely fresh provision. **Not** reproducible in either
harness: the same disk mounts `/usr` silently under the desktop `vax780` *and*
under `libsimh`, with `set cpu idle=4.1BSD` on or off. So the disk was fine, the
simulator was fine, and the fault was the app's.

### Two bugs, one line apart

`waitForHalt` waited for **`"halting"`**, which is V8's word. V8's `boot()` calls
`update()`, prints `syncing disks... done` and then `halting (in tight loop)`
before spinning at IPL 31 — so that word means the I/O has drained, which a timer
never would. **V10's `boot()` is two lines** (`lsys/md/machdep.c`):

	boot(howto) { if (howto&RB_HALT) death(); reboot(1); }
	death() { splx(0x1f); printf("death\n"); for (;;) ; }

It prints **`death`**. So the wait timed out and the provisioning restart
relaunched over a guest that had confirmed nothing.

And V10's halt neither syncs **nor unmounts**, so `/usr` kept `s_valid = 0`.
`fs.c:107` refuses a bitmapped filesystem whose `s_valid` is clear, and only
`fsoff` — a real unmount — sets it back. The next boot could not mount `/usr` and
carried on into multi-user with root's empty `/usr` showing through: the failure
CLAUDE.md already describes in those words, met in a new place.

`relaunchProcess()` was **not** at fault, which is worth saying because it was my
first suspicion: it is called *after* a halt. The halt is what was not confirmed.

### Both are properties of the machine

	                 V8                          V10
	haltMarker       "halting"                   "death"
	shutdown         cd /; sync; sync            cd /; sync
	                 /etc/halt                   /etc/umount -a
	                                             sync
	                                             /etc/halt

The `umount -a` is the load-bearing line. The two syncs around it are because
V10's `sync(2)` sets `B_ASYNC` and returns before the disk has the block
(`lsys/io/bio.c:692`) — which is what `v10drive.exp`'s `v10_halt` already does.
V8's list is unchanged.

### Verified in both directions

On a fresh provision, in the app:

	if test -d /usr/bin ...              -> USR-MOUNTED
	/usr/bin/wc -l /etc/ttys             ->       9  /etc/ttys
	/usr/bin/find /usr/lib -name libm.a  -> /usr/lib/libm.a

so **our own built `wc` and `find` are running off K10.2's libraries**. And after
a clean quit the disk reads back **`s_valid = 1`** — left remountable, rather
than needing an `fsck` that V10 has no autoboot for.

**Found only by launching the app and dialling a line.** Nothing in the build,
the config, the boot transcript, `app-check` or K14's 23 assertions could have
shown it — K14's boot 2 halts cleanly, so the disk it leaves is correct. The
defect was in what the app did to it afterwards. The general form is worth
keeping: **a harness that tears down correctly cannot discover a teardown bug in
the thing that ships.**

## 20. "A second machine beside V8" cannot mean simultaneously

The roadmap has said since Track B was scoped that V10 would be *"a second
machine beside this one rather than a replacement for it"*. That was written
before this was known, and one word in it is wrong: **beside cannot mean
simultaneously**, in one process. Four independent pieces of evidence, none of
them new work:

**The app already says so, describing a met failure.** `Machine.swift`:

> The simulator is a thread inside this app, and SIMH cannot be run twice in one
> process: its globals are never reinitialised, so a second `simh_main` walks the
> first session's event queue and `sim_cancel` calls `abort()`.

It is the entire reason `relaunchProcess()` exists.

**It was met by accident, and it crashed.** `Machine.start()` guards on its own
flag rather than on `phase` because two windows appearing in one runloop turn
both spawned a SIMH thread — *"two VAX-11/780s inside one process, binding the
same ports and attached to the same `v8.disk`. It died on the spot, which was the
lucky outcome"*, two simulators on one disk being this project's central
corruption hazard.

**The globals are pervasive, not incidental.** File-scope definitions:

	scp.c          ~1,250
	sim_tmxr.c       ~309
	vax_cpu.c        ~155

Making the core re-entrant is a rewrite of upstream SIMH, not a refactor here.

**And the ports are per-process.** `portBase` is

	42000 + UInt16((pid &* 2_654_435_761) % 8_997)

a function of `getpid()` alone — so two `Machine` instances compute the *same*
base and bind the same ten ports. The failure mode is the documented one:
`scp.c`'s attach loop is gated on `r == SCPE_OK` and never resets `r`, so the
first bind failure silently skips every remaining attach, and since the DZ
precedes the disk in device order the machine comes back **with no disk**.

So **one machine at a time, selected in Settings, is the reachable design** —
not a stepping stone toward two. Each edition keeps its own support directory,
disk, snapshot and terminal state, so switching disturbs neither. Two at once
would need a second *process*, an XPC-style split iOS does not allow for this
shape of app.

Recorded as settled in CLAUDE.md and in the plan, because an open task that
cannot be done is worse than a closed one: it gets picked up again.
