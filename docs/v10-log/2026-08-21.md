# 2026-08-21 — rung 10: reading the disk, and the shell that was never there

K15 closed rung 8's host half yesterday. Rung 10 — a shippable `v10.disk` —
had one open question recorded in the plan: *"the real open question is where
the staged root comes from"*, K10.3 installing into `/usr/w10` on one image
chain while K14 builds disks on another.

That question dissolved in a minute and a much worse one took its place. Every
measurement below is host-side; **no simulator ran until the source-disk
rebuild at the end**.

---

## 1. The sequencing question was not a question

`.k13` is `stage1.k102.k7.k13` — it **descends from `.k102`**, so the
disk-building machine already carries K10.2's 26 archives, which is K10.3's
only precondition. Confirmed by reading the image rather than by booting it:
`/usr/lib` holds all 26 plus `yaccpar`, and `/usr/s1` holds stage 1's complete
toolchain. So K10.3 runs on the `.k13` chain and one machine carries
everything.

The tempting shortcut was to extract `/usr/w10` from the existing `.k103`
image host-side, serve it over netfs and let K14 copy it in — saving a
40-minute relink and losing nothing in provenance, since `.k103` and `.k13`
share the same `.k102` ancestor. **Rejected**, and the reason is worth
keeping: that would put the new reader in the *build* path as well as the
*verification* path, so a bug in it would write and then bless the same wrong
bytes. Circular verification is the failure this project keeps cataloguing
(*"two readings agreeing is not two readings being right"*). The reader stays
an instrument.

## 2. `tools/v10fs.py` — and it is proven, not reviewed

`v8fs.py` for the Tenth Edition. Its argument applies twice over here,
because a V10 guest is a poor witness about its own filesystem: `ls` exits 0
for a file that does not exist, and a full filesystem **sleeps** rather than
failing.

The trap the file exists to get right is that **a block address has two
encodings**. The inode packs 13 addresses at three bytes each — `l3tol`, whose
**vax** arm is three bytes little-endian with a zero high byte, where the
pdp11 arm of the same file packs the identical bytes in a different order —
while the indirect blocks hold full 4-byte `daddr_t`, because `bmap()` reads
them as `b_un.b_daddr` sized `BSIZE/sizeof(daddr_t)` = 1024.

Every constant is quoted from the tape: `lsys/sys/ino.h` (64-byte dinode),
`lsys/sys/dir.h` (DIRSIZ 14, 16 bytes), `NADDR` 13 (`lsys/sys/inode.h:12`),
`itod`/`itoo` (`param.h:86`), `fsbtodb = b*8` (`param.h:88`).

**The proof is nine binaries extracted from the golden and byte-identical to
the tape's own prebuilt copies:**

	sh  ls  ps  make  sed  diff  pr  test  as

`as` is 57,203 bytes — fourteen blocks — so it goes through the single
indirect. That cannot come out right unless `itod`, `itoo`, the `l3tol` arm,
the 3-vs-4-byte split, `NADDR`, `NSHIFT` and `NMASK` are all correct at once.
It is a much stronger check than the block accounting that preceded it: block
counts can agree while a constant is subtly wrong, because an off-by-one in
`itoo` still yields *a* 64-byte inode.

Block accounting agrees anyway, to within four blocks of 516 and two of 1547,
the residue being what `mkbitfs` marks rather than what this reads.

### The `prov` verb, and both of its false readings

`prov` splits a disk's files into the tape's bytes and ours. Both faults ran
in the **flattering** direction, which is the sort that survives review.

**An empty file is not evidence of anything.** `/etc/mtab` and `/etc/utmp` are
zero bytes, every empty file has the same sha256, and the tape happens to
carry one (`blit/demo/mpx/.jciferr`) — so the oracle credited Bell Labs with
two files this project had truncated.

**And an archive identical in every member read as foreign.** The golden's
`/lib/libc.a` differs from the tape's in exactly **ten bytes**, all of them
the `__.SYMDEF` member's ar-header timestamp:

	tape   743340498     (mid-1993)
	disk  1786908310     (August 2026)

because CLAUDE.md requires re-`ranlib`ing an archive at its destination — `cp`
bumps the mtime and that alone demotes a good archive to V10 `ld`'s
single-pass case 3. **The re-ranlib is correct and the whole-file hash called
the correct thing foreign.** Archives are now fingerprinted per member with
`__.SYMDEF` dropped, which is stage 2's own per-member-witness discipline.

### First findings, none of which needed a boot

	base golden      /unix = lsys/astro/seki.u    Bell Labs', for another machine
	.k7 and later    /unix = 228,310 bytes        ours, from ipnx780.m
	K14's built disk root 61 files / 2.1 MB      complete boot path
	                 /usr  1 directory, 0 files  EMPTY

`/unix`'s `addr[]` on the built disk is **ten direct plus one indirect**, which
is `lsys/boot/README`'s *"no more than singly indirect"* satisfied to the
letter.

## 3. `sh` was specified into `/usr/bin`, and `/usr` is a separate filesystem

This is the day's real finding, and it would have produced a disk that boots
and then stops.

	world.link:231    sh /usr/bin default -

`default` means *"ours, because it had to go somewhere"*. `where.txt` had **no
row for `sh` at all**, because `commands()` asked *"does `cmd/X` hold `X.c`"*
and `cmd/sh`'s main is `main.c` — the same blind spot the `MK` comment already
recorded for the toolchain, silently dropping **92 units**.

Why it matters, measured rather than reasoned. Strings out of the golden's own
`/etc/init`:

	/bin/sh   /etc/getty   /etc/rc   /etc/ttys   /etc/utmp   /usr/adm/wtmp

and `/etc/rc` entire:

	PATH=/bin:/etc:/usr/bin
	export PATH
	/etc/mount /dev/ra0c /usr
	cat /etc/motd

So `init` execs `/bin/sh`, and the shell it execs is what runs the script that
mounts `/usr`. A shell only in `/usr/bin` **does not exist at the moment it is
needed** — V8 stage 8's disk that *"walked 4,507 files and then stopped dead
after autoconfig with the CPU idle"*, on the Tenth Edition.

### The fix is to read what the tape already says

`where.txt` carried five hand-transcribed install rules and inferred the rest.
`mk_paths()` now scans each unit's own makefile for `cp <name> <dir>` and finds
**43**.

	10 commands MOVED to the directory the tape names
	   sh make tp kasb -> /bin       config dump -> /etc
	   diff3 apsend style -> /usr/lib     map -> /usr/maps
	30 more kept their directory and gained real evidence (22 mkfile, 8 v8)
	where.txt 266 -> 347 rows

Two of the moves look odd and are historically right: `diff3` belongs in
`/usr/lib` because `diff -3` invokes it, and `map` really is installed to
`/usr/maps`.

**The source token must be the product's own name**, which is what separates an
install from a backup. `cmd/sh/makefile:37` is three commands on one line:

	mv /bin/sh /bin/osh;	cp sh /bin/sh;	strip /bin/sh

The **first** would answer `/bin/osh` to a scanner reading destinations.
Matching `cp sh …` gets it right and rejects `cp $(FILES) /usr/src/cmd/make`
at the same time. Continuation lines joined first, recipes split on `;` — both
of them rules this project already had.

### And a second list said otherwise

`prebuilt.txt` hardcoded `TOOLCHAIN = {as, ranlib, lex, make, sh, sed}` to fill
that very hole. The scan agrees with five and **contradicts the sixth**: it
said `sed → /bin` where the tape (`cp sed /usr/bin`) and V8's measured disk
both say `/usr/bin`. So the hardcoded value was simply wrong. `sed` is removed
with its reasons recorded, the five that agree stay as a **live control**, and
both generators now halt on a disagreement.

Both guards were proved to bite before being trusted — claiming `as` lives in
`/usr/bin` stops `v10-where.py`, claiming `make` does stops `v10-prebuilt.py`
— which is the only reason a useless guard ever gets found.

**A note on circularity, checked before relying on it.** The first idea was to
add a `gold` source: measure install paths on V10's own disk. That is
**circular** — `prebuilt.txt` uses the same authority scheme (`man`, `v8`,
`toolchain`, `default`) and 30 of its 57 rows are `default`, so the golden's
layout *is* our earlier inference read back. Dropped.

## 4. What a shipped disk carries — decided on measurement

The instinct is to keep Bell Labs' binary wherever one exists. CLAUDE.md rules
that out in its own words: the 46 prebuilt commands are *"developers' working
directories, so what survived is whatever was last compiled in place"*, and
they are *"an ORACLE, not a shortcut … use the 46 to check what we build, never
to skip building it"*. Build detritus is not a specification; the **source**
is, and K10.3's 203 commands were built from it by V10's own compiler. Stage 2
settled the identical question the identical way.

So: **our build where we have one, the tape's where we do not.** The 40
prebuilt commands we cannot build — `2500 adb bcp picasso lcc lex …` — keep
Bell Labs' bytes untouched, because nothing overlays them.

How much the choice actually decides, measured:

	K10.3 staged                       203 files, 6.5 MB
	  collide with a builder path       50
	  new                              153
	of the 50 collisions
	  Bell Labs' own bytes              19
	  ours already                      31
	sampled collisions, text+data identical    9 of 10

So the build is **deterministic in generated code** — the differences are
twelve bytes of symbol table, one entry, the source path — and "which build
wins" is a real question for almost none of them. The exception is
`/etc/login`, genuinely smaller in K10.3's build (text 22528 → 20480), which is
the documented Share-scheduler removal.

**And it is safe to overlay, which was checked and not assumed.** V10's `ld`
writes its output even when symbols are undefined; it reports them and
**clears the execute bits**. All 203 staged files carry `x`, so `ld` resolved
every symbol in every one.

## 5. K14 fills `/usr`

Root gains K10.3's `/bin` (37), `/etc` (31) and `/lib` (1); `/usr` gains the
tape's 40 commands plus K13.1's four, K10.2's 26 archives, the headers, the
5620 tree where K15's `mux` lands, the Blit tree its libraries came from, and
`games`/`adm`/`tmp` — `adm` because `/etc/init` writes `/usr/adm/wtmp`, read
out of init's own binary.

Not carried, each for a stated reason: `obj`, `k13obj`, `k14obj`, `k10lib`
(scratch and logs); `s1`, stage 1's **staging** tree, because the toolchain is
already installed at its system paths and this is a second copy under a name
nothing references; and `w10`, whose contents are overlaid at their real paths
while the directory itself must not ship.

**The previous disk lost three commands and nothing said so.** K13.1 installs
`find`, `cpio` and `wc` into `/usr/bin`, and K14 copied only `/bin /etc /lib
/dev` — so the disk V10 built could not walk a filesystem, i.e. could not
build the next one. There is now an assertion for exactly that.

The driver reads the finished image's **contents** rather than only its
superblock, and checks the boot path by *property* — a regular file, non-empty,
executable, since `x` is `ld`'s verdict. Proved against K14's existing output
before being trusted, where it correctly refuses:

	/usr holds no files at all, so this is not a system

## 6. Two process faults, both mine, both cheap

**`"$IMG:c"` in zsh silently drops the `:c`.** `$K:c` is a history modifier, so
the argument arrives with no partition, defaults to root, and the tool
truthfully reports that `/bin/lex` is not there. **Nine files read as MISSING
when all nine existed.** An RA81 image holds two filesystems, so this is K11's
*"a guest can report success about the wrong disk"* moved to the host.
`${K}:c` is the fix in the shell; `v10fs.py` now prints the filesystem it read
on stderr every time, because a banner is the only thing that makes the wrong
answer visible instead of plausible.

**`nohup … &` inside a backgrounded call reported "exit 0" over a run that was
still booting.** The ampersand makes the wrapping shell exit immediately, so
completion was announced while `vax780`, `expect` and the driver were all
alive — and the log at that moment stopped mid-`attach il nat:`, which looks
exactly like the documented SLiRP bind failure. **Nothing was damaged, and
only not starting the next run on top of it kept that true.** Checked for a
live simulator before doing anything else; found one; waited.

Also caught by checking rather than by reading a summary: `v10-world.py` needs
`--write`, and a bare run prints its survey and writes nothing. I nearly
recorded "0 rows moved" as a result about the fix. `git diff` being empty is
what caught it.

## 7. The simulator is a property of the image, and K10.3 hardcoded it

The first attempt to run K10.3 on the `.k13` chain panicked in the boot:

	unix
	type 2 sp x7fffec00 code x0 pc x800139f8 ...  panic: trap
	type 8 sp x7fffec00 code x0 pc x80009581 ...  panic again: trap
	HALT instruction, PC: 80000BB3 (HALT)

`v10-link.exp` spawns **vax750**, because K10.3 was written for the `.k102`
chain. The `.k13` chain's `/unix` is our own `ipnx780` kernel, which dies on a
750 for hardware that is not there — `ms780`, `dw780`, `mba`. Two separate
faults, fixed separately.

**The harness took eight minutes to say so, and then said the wrong thing.**
`v10_must "ogin" 480` reported *"never saw 'ogin' after 480s"* — the symptom.
The diagnosis came from reading the transcript by hand.

**`v10_select_machine` asks the kernel.** K7's kernel carries its own banner
string, `Unix 10e ipnx 780`, which is the line K9's transcript prints on the
console; `lsys/astro/seki.u` does not. `tools/v10fs.py` reads it off the image
host-side, with no simulator, and the simulator follows. That is a measurement
of the artefact rather than a convention about its filename — the same reason
provenance here comes from hashes and never from grepping a binary for
`vaxpcc2`.

	golden                 no ipnx780 banner  ->  vax750 + uda750
	.stage1.k102.k7.k13    ipnx780 banner     ->  vax780 + uda (star)

**`v10_must_boot` makes a panic a first-class outcome**, so the next one fails
in seconds naming the likely cause. Two expect traps avoided deliberately, both
already recorded in CLAUDE.md: **no `--`**, because it ends option processing
and would silently turn a later `-re` into a literal glob; and the **flat**
form, the only one of expect's three spellings that both honours `-timeout` and
re-splits into pattern/action pairs.

Proved against real processes rather than under the dry-run's stubs, because the
success path is the one that would break every harness:

	prints `login: '      -> matches, boot proceeds          exit 0
	prints `panic: trap'  -> bails at once, names the cause   exit 7
	prints nothing        -> bails at the timeout, 3s         exit 7

The third is not redundant: it confirms `-timeout` is still honoured with four
pattern pairs.

**Nothing was at risk while this was found, and that was the clone rule rather
than luck.** Both attached images were clones; `.k13` itself still reads its
original mtime. The orphan check showed the simulator idle at `sim>` — 0.0% CPU,
state `Ss+`, parent alive — rather than spinning, and the harness reaped itself
and reported the clone as damaged:

	V10-BAIL: never saw 'ogin' after 480s
	V10-BAIL: guest stopped at sim> and quit -- NOT cleanly halted,
	V10-BAIL: so treat this image as damaged until a hash says otherwise.

## 8. `$var:` followed by a letter, twice in one hour

The zsh modifier trap from §6 recurred as **`:a`** — the absolute-path modifier
— in a loop over image names, so every read returned nothing and it looked like
an empty kernel rather than a wrong path. The call said `2>/dev/null`, which
also suppressed the banner added an hour earlier to catch exactly this.

zsh's modifiers are a family (`:h :t :r :e :a :A :c :l :u :s`), so **any**
`$var:` followed by a letter is a hazard. Always `${var}:part`. And a banner on
stderr does not help a call that discards stderr.

## 10. `sh$` does not match `sh\r`, and the report said so out loud

The run printed

	sh did NOT build, and it is the generic recipe's limit rather than
	a fact about the tape ...

three lines from a log containing `CLINKED sh`, over a staged root holding a
57,494-byte `/w10/bin/sh`. The test was

	if ! grep -qE 'CLINKED sh$' "$LOG"

and `CLINKED` is echoed by the **guest**, so it arrives through the tty as
`CLINKED sh\r\n` — and BSD grep's `$` anchors *after* the carriage return. The
test was permanently true. The anchor cannot simply be dropped: unanchored,
`CLINKED sh` also matches `CLINKED showq`. `[[:space:]]*$` keeps the anchor and
tolerates the `\r`.

**The distinction that matters, checked rather than assumed.** Four sibling
harnesses anchor on `$` over the same logs and every one is correct, because they
match lines *expect* printed with `puts` — `\n` only. This was the only one
matching a line the guest printed. Measured on the real logs, anchored count
against count-after-`tr -d '\r'`:

	v10-link.sh    CLINKED sh$          0  vs  1   <-- broken
	v10-mux.sh     the oracle.*ok$      2  vs  2
	v10-stage2.sh  NO$                  0  vs  0
	v10-stage3.sh  FIXPOINT.*ok$        7  vs  7
	v10-stage3.sh  FIXPOINT.*NO$        0  vs  0

So one site is fixed rather than five changed blindly. **Anchor freely on our own
output; never on the guest's without allowing for the `\r`.**

It hid twice over. A permanently-true test stops being read — the same mechanism
that let `atof` hide in stage 2. And checking the pattern by hand **confirmed the
opposite**, because this shell's `grep` is a ugrep shim that treats `\r\n` as the
line terminator, while the harness runs BSD grep under `bash`. *Test with the
tool that runs.*
