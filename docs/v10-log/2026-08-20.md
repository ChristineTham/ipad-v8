# 2026-08-20 — the netfs fault, measured instead of inferred

K15 ended yesterday at 6/12 with a build that died on

	"/n/tree/src/history/ix/src/jerq/mux/32ld.c":214:syntax error
	"/n/tree/src/history/ix/src/jerq/mux/32ld.c":214:saw EOF

over a **295-line** file. Today's work was not on mux at all: it was on the
three claims I had attached to that failure, two of which were wrong, and on
building instruments so the next reading cannot be argued about.

---

## 1. The guest is NOT starved, and the number that said otherwise was mine

`tools/v10-clock.sh` — fixed local guest work (`cat /unix > /dev/null`,
228,310 bytes off local disk), timed by the **host**, card attached and then
disabled, three reps, median. No network in either arm.

	il off    46, 44, 44 ms      median 44
	il on     69, 193, 72 ms     median 72
	                              ratio 1.64x

**The harness refused to draw a conclusion**, and its refusal was correct
policy even though the effect is probably real: 1.64× lands in the band it
declines to interpret, and 44 ms of work is close to the tty round trip that
measures it. What the reading *does* settle is the question it was built for —
**a guest that reads 228 KB in 72 ms is not too starved to issue netfs
requests.** Nothing about a 1.64× tax can produce a multi-second request.

The `off` arm is tight to ±2 ms and the `on` arm is 69/72 with one outlier, so
there is very likely a real ~64% cost to having the card attached. That is worth
knowing and is not today's bug. Raising the workload is the way to settle it,
which is what the harness already tells you to do.

---

## 2. "~9.6 s per request" was a request RATE, not a service time

This is the correction that mattered most, because every other reading was being
interpreted through it.

netfsd's trace **has no timestamps** — I checked, rather than remembering. So
the figure could only have come from one place: the run's elapsed time divided by
`connection closed after 399 requests`. That is a request *rate*, and a guest
that spends most of its time compiling produces exactly that number without the
server being slow at all. The units read as latency because of the words "per
request".

CLAUDE.md already records this error twice — the withdrawn "530 file reads in
2 s", and `used = s_fsize - s_tfree` counting the i-list as content. Same shape:
**a quotient whose divisor does not mean what the units imply.**

### The instrument, so it cannot recur

`netfs/Sources/NetFS/Server.swift`'s connection loop already had the boundary in
it — `wire.readExactly()` *blocks* until the guest asks, so time inside it is the
guest's and time inside `serve()` is ours. Two monotonic counters (`DispatchTime`,
not `Date`, because this process runs for hours beside a guest that thinks it is
1976) now split them, and the closing line reports:

	connection closed after N requests  (serving X ms total, Y ms mean,
	                                    Z ms worst; waiting on the guest W s)

### And the honest replacement figure

Measured today on a workload with **essentially no guest computation** — `wc -c`
and `cat` over a share, nothing compiled — by sampling netfsd's request count
across a 90-second window mid-run:

	12 requests in 90 s   =   7.50 s per request

Same order as the K15 figure, but now on a workload where the divisor means what
the units say. **So netfs really is seconds-per-request slow; the K15 number just
could not have proved it.**

## 3. The truncation is real, and it is EXACTLY one block

Host-side, no simulator, one command:

	32ld.c is 5870 bytes, 295 lines
	head -c 4096 | wc -l   ->   213

and cpp reported the error at line **214**. netfsd served one
`NREAD count=4096 off=0` and was never asked again. So cpp saw exactly the first
block and took it for the whole file.

**Three 4096-byte replies in the same run were served perfectly**, which retracts
the frame-size hypothesis I was carrying:

	mpx.h      4096 @ 0,  804 @ 4096, 0 @ 4900    complete
	pads.h     4096 @ 0, 1247 @ 4096, 0 @ 5343    complete
	filehdr.h  4096 @ 0, 1134 @ 4096, 0 @ 5230    complete
	32ld.c     4096 @ 0   -- and nothing, ever    TRUNCATED

A full-size reply is not what breaks. The failing read also never sent `NPUT`
for its tag, where every completed read does — the shape of an abandoned handle.

`naread()` (`lsys/fs/neta.c:222`) is a clean read-until-short loop that never
consults `i_size`, so it behaved correctly: the caller asked for 4096, got 4096,
`u_count` hit zero, loop ended. **The fault is above it — in a second `read(2)`
that never reached the wire.**

## 4. The probe: two readers, because one cannot localise it

`tools/v10-netread.sh` + `.exp`. No compiler, no build, no libraries — `wc -c`
against the host's own `stat` is the whole measurement, which is why it costs one
boot instead of the fifty minutes K15 spent to find this once. Every file is read
three times, because K14 read a 5106-byte file correctly on the same transport
and a single clean pass proves nothing.

**Two readers, and the split is the point:**

	wc   NBUF = 64*1024  (cmd/wc.c:3)     ONE read(2); naread()'s own loop works
	cat  BLOCK = 4096    (cmd/cat.c:8)    REPEATED read(2) -- cpp's exact pattern

cpp's `refill()` does `read(fileno(fin), pbuf, BUFSIZ)` and r70's `stdio.h` makes
`BUFSIZ` 4096, so `cat file > local` reproduces the failing pattern precisely,
and `wc` tests the other path. A probe with only `wc` could have passed while the
bug stood.

### Two traps caught host-side, before spending a boot

- **`wc -c` prints `%7ld`.** `printout()` right-aligns in seven columns, so
  `` n=`wc -c < f` `` yields `"   5870"` and a quoted `test "$n" = 5870` is false
  for **every** file. The probe would have reported total truncation over a
  working transport. Unquoted, sh's field splitting discards the padding.
- **`show il stats` has never worked.** pdp11_il.c's MTAB row names
  `"STATISTICS"` and SIMH matches in full, so the command answered
  `%SIM-ERROR: Non-existent parameter: STATS` — which was not one of
  `v10_ilstats`'s patterns either, so it fell through to a 30-second timeout and
  the reading was silently absent from every V10 halt since it was added. Fixed,
  and the error text is now matched explicitly so a future rename is loud rather
  than slow.

## 5. A mechanism from Bell Labs, in their own words

`ilincmd()` waits for a command-completion interrupt with
`tsleep((caddr_t)is, PZERO, 5)` and `slp.c:86` declares that third argument
`seconds` — a **5-second** timeout, tantalisingly close to the measured 7.5 s.
**It is not the cause**: its only callers are lines 180/195/207, all
`ILC_RESET`/`ILC_STAT`/`ILC_ONLINE`, i.e. init. Recorded because I believed it
for several minutes.

The hot path carries something better sourced. `lsys/io/ni1010a.c`:

	/*
	 * add receive buffer space if needed
	 * -- let it be an ordinary command, interrupt when complete, for now.
	 * this is probably too slow
	 */
	ilrcvbufs(is)
	{
		if (is->flags & CMDACT)
			return (0);

**Bell Labs flagged this path as slow themselves.** `ilrcvbufs()` posts *one*
buffer per command and refuses to post while any command is active; it wants
`ILRBYTES` = `ETHERMAXTU*2` = 3000 bytes in `ILRSIZE` = 1024-byte blocks, so
three buffers, each needing its own command and its own interrupt round trip.

**V8's `ill.c` chains instead** — `bp->next = allocb(n)`, with the next buffer
supplied from *inside* `ilrint()` — so it never pays that round trip. Same card,
same device model, different driver. That is the right shape to explain 7.5 s
against the ~16 ms per request `pdp11_il.c:775` records for *unpatched* V8, a
**470×** gap on identical simulated hardware.

It is a mechanism and not yet a measurement. `show il statistics` (drops, now
that the command name works) and netfsd's serving-versus-waiting split are what
decide it, and both arrive with the probe's first complete run.
