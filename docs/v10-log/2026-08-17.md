# 2026-08-17 — stage 2, and the tape is a working tree

Goal for the session: build libc from V10 source on V10 (stage 2), then the stage-3
fixpoint. Stage 2 landed as a measurement rather than a pass, and the measurement
turned into the most important finding on Track B so far.

## The finding: there was never a pure V10

**V10 was not built and shipped. It was hand-built on each machine by upgrading V9 in
place, and the tarball is one such machine's working tree caught mid-migration.**

Christine read it before the evidence did — first *"V10 was never a clean build but
patched up over the years"*, then *"the tape binaries may not be from a working system
at all, but from someone's active source tree with partial binaries recompiled"*, then
*"someone was trying to port libc from one compiler to another but left the job
unfinished"*, and finally *"the old ones were from V9"*. Every one of those turned out
to be checkable, and every one checked out.

### The `ar` headers settle it in one command

A clean build dates every archive member within minutes of itself. `libc.a` does not:

	1989-06             199 members      <- one build
	1989-08 .. 1993-07   62 members, in ones and twos across 26 more days

4.1 years, 27 distinct days. So it is a June 1989 archive with four years of piecemeal
`ar r` on top — which is exactly the reading this project already applies to the 46
prebuilt command binaries: *what survived is whatever was last compiled in place.*

### And the old members are V9's

Correlating the dates against what stage 2 can reproduce:

	C members from June 1989    105, of which 90 differ from ours   (86%)
	C members recompiled later   59, of which 19 differ             (32%)

**The members we cannot reproduce are the old ones.** Our compiler is stage 1's, built
from the tape's *1995* `cmd/ccom/vax/` source, so it resembles the late compiler — and
the 1989 compiler is not on the tape. All 97 assembly members match, because `as` is
stable across the whole span; every difference is C compiled by a compiler that no
longer exists.

The tooling corroborates the dates rather than merely permitting them:

- lcc's VAX back end is `cmd/lcc/gen2/`**`vax-v9`**`/rcc`
- the prebuilt lcc driver (`etc/lcc`, compiled from `bowell.c`) passes **`-DV9`**
- libc's own `mkfile` passes **`-DV10`**

A V9 libc being migrated to V10, one member at a time. We have no V9 VAX source, so
those objects are unreproducible *in principle*, not merely in practice.

### Four candidate explanations, all eliminated by measurement

Before reaching for provenance I tried the mechanical explanations, each over all ~110
differing members, each reporting its own count in `tools/v10-stage2.sh`:

| candidate | matches |
|---|---|
| stage 1's `ccom` (`cc -B/usr/s1/lib/ -t02p -O`) | 149 of 261 overall |
| the tape's own prebuilt `comp` (`cc` with no `-B`) | 0 additional |
| `cc` without `-O`, i.e. no `c2` | 0 additional |
| `lcc` | 1 additional — `atof.o`, dated 1991-12-19 |

That one lcc match is what proved the migration was real: a member whose bytes are
lcc's and nobody else's.

## Neither compiler can build libc alone

Christine's fallback was *"the best version you can, preferably from a single compiler
rather than a mixture."* Measured over all 261:

	cc alone      246 of 261 build      (fails 9 printf family + 6 shares)
	lcc alone     202 of 261 build
	cc + lcc      246 of 261 build      <- current stage 2

So a single compiler is not available even as a fallback — and that is itself the
strongest evidence for the migration reading: **the tree needs both because it was left
half-converted.**

Two hard limits found on the way:

- **`<shares.h>` is on no machine we have.** `getshares`, `getshput`, `openshares`,
  `putshares`, `setupshares` and `setlimits` include it; it is in none of the 25,682
  files, though their objects sit in `libc.a`. It existed once, on the machine that
  compiled them. I first misfiled these as an ANSI problem; the error is
  `syntax error; found 'share' expecting ';'` — an undeclared type.
- **`stdio/iolib.h` has no branch for a V10 VAX.** It covers *V10 without stdarg*,
  *pANS with stdarg* and *SGI*; under the mkfile's own `-DV10`, `va_list` is declared
  only when `sgi` is also defined. So the nine `printf`/`scanf` members fail under
  *both* compilers. The fix is a named one-line patch in `v10/src/` on the
  `mv.c`/`fsck.c` model, not `-Dsgi` on a VAX.

Ceiling from source is therefore **255 of 261**.

## Stage 2 as it stands

	261 members expected
	150 byte-identical to the tape's
	246 build (15 fail: 9 printf family + 6 shares)

`v10/mk/gen/libc.mk` is generated from the tape's own `mkfile` — `libc_from_tape()`
parses it and refuses to run unless its object list and `libc.a`'s member list agree —
with member **order** read out of the archive, because V8's `lorder | tsort` recipe
needs two tools the V10 golden does not have and the archive is Bell Labs' own answer
anyway. `LIBC_LCC` carries the 26 members that need lcc, measured rather than taken
from the mkfile, which names ten and is wrong about sixteen.

## Harness work this took

Four defects, all of which cost runs before they were understood:

- **`expect` has three spellings and two fail silently, in opposite directions.**
  `expect { -timeout N … }` never times out; `expect -timeout N { … }` never *matches*
  (`exp_internal` shows a braced body after a flag being read as one glob pattern).
  Only the flat `expect -timeout N -- "pat" {} timeout {}` does both. The first held
  two completed stage-1 runs at `sim>`; converting to the second as "the fix" made
  teardown terminate on time and stop matching `death`.
- **A harness must terminate itself.** Both drivers now end every path in a
  `close`-based reap and carry an `after` watchdog, which fires even inside a blocked
  `expect`. Halt path: hung forever → 900 s → 157 s → **7 s**.
- **V10's `umount` takes the mount point, not the device**, and `/usr` must be
  unmounted or the next boot runs with the root filesystem's empty `/usr` showing
  through. That cost a run in which `/usr/s1` and `/usr/bin/ranlib` were invisible and
  255 members "failed to compile".
- **The prebuilt lcc emits empty objects and exits 0** when its `-undef` reaches a cpp
  that rejects the flag. V10's own `/lib/cpp` warns and carries on, so the authentic
  `bowell`-configured driver works with the tape's own preprocessor. *An object file is
  not evidence that a compiler ran.*

## What this changes upstream

- `README.md` and `docs/v10-restoration.md` now say plainly that ipnx's V10 is a
  **reconstruction**, and why it cannot correspond to a real V10 machine: no two real
  V10 machines corresponded to each other either.
- V9 is still skipped as a build target, but it is no longer irrelevant — we stand on
  top of it without a copy of it.
- V11 gets the standardisation (ANSI C, one compiler); the Plan 9 compiler needs a VAX
  back end reconstructed (roadmap D-A4) or a non-VAX target (v12).

## Later the same day: stage 3, and the member nobody counted

Stage 3 was written and run. It builds five of the seven toolchain components and then
stops, and what stopped it is worth the whole entry:

	stage 3 built ccom     NO
	stage 3 built as       NO

	Undefined:
	_atof

`atof.o` was never in our `libc.a`. `libc/gen/atof.c` is seven lines and one of them is
`atof(const char *s)`, which pcc2 cannot parse — so the member was simply absent, and a
**link two stages downstream** was the first thing to report it.

### Stage 2 had said so, and the host counter dropped the line

This is the part to remember. `tools/v10-stage2.sh` counted missing members with

	grep -oE '^MISS [A-Za-z_0-9]+\.o$'

and the log contained

	MMISS atof.o

`v10_run` sends a command and *then* reads, so the tty echoes the tail of what was typed
into the **first line of output** — every time, structurally. The comment above that grep
asserted the opposite ("the guest prints these under `v10_run`, so no marker echo is
spliced through them"), which is true of the body of a dump and false of its first line.

So the run reported one missing member where there were two, and CLAUDE.md recorded *"the
ceiling is reached: the only member that does not build is `setupshares`"*. The real
figure was **259**. The guest's own verdict —

	all 261 members compiled     NO

— sat four lines above a summary that contradicted it, and nothing in the run compared
them. Two witnesses in one log, one of them right, neither reading the other.

### One compile error, three failed assertions

Two of these were being carried as separate open questions:

| assertion | actual cause |
|---|---|
| `all 261 members compiled` NO | the prototype |
| `member list and order match the tape` NO | `atof.o` absent from the archive |
| `install` NO | `make install` retries the missing object and dies on it |

The standing hypothesis that `install` failed on a `-mkdir` V10's make would not honour
was **false**. It honours the dash exactly as documented — `*** Error code 1(ignored)` —
and install never reached the mkdir. *When several assertions fail together, look for one
cause before theorising three.*

### The diagnostic probe reported success for a failed build

Added the round before to dump an unfiltered `make`, it printed:

	cp comp /usr/s3/lib/ccom
	RAW3RC=0

V10's `ld` **writes its output file even when symbols are undefined** — it reports them
and clears the execute bits — so `comp` was already there and newer than its
prerequisites. make skipped the link entirely and ran only the install step, whose status
is what got printed. Reading the return code alone would have closed this bug as
nonexistent, and the probe *installed the broken `ccom`* on its way past.

It was justified at the time on the grounds that "a probe that prints output cannot break
the build". That is wrong twice over: it re-ran a build step with side effects, and a
probe that can report success for a failure is worse than no probe at all. Removed — the
filtered dump answers the question anyway, because it deletes *compile* lines and a link
diagnostic is not one.

### The fix, and why one line of it must not move

	 double
	-atof(const char *s)
	+atof(s)
	+	char *s;
	 {
	 	return(strtod(s, (char **)0));

The `#include <stdlib.h>` **stays**, and that is the whole subtlety. K&R C defaults an
undeclared function to `int`, so dropping the include would truncate `strtod`'s `double`
to a word and give a silently wrong `atof` — far worse than a compile error. r70's
`include/libc.h` line 15 is

	extern double atof(), strtod();

exactly the K&R declaration this needs, and `/usr/include/stdlib.h` (installed from
`include/CC/stdlib.h`) is six lines onto it.

### Guards, so a member cannot hide again

- Every host-side counter matches its token **unanchored**, in both wrappers.
- The three stage-3 verdicts go through guest variables (`echo $S $name`), so no command
  echo carries the literal token. This is needed *before* unanchored matching is safe:
  `echo SAME yacc` would otherwise put the answer in the log whatever the answer was, and
  the host would count the question. Two fixes, two different faults, both required.
- `tools/v10-stage2.sh` refuses to print a measurement when the guest asserts a member is
  missing and the host counted none.
- `grep -c` prints `0` *and* exits 1, so `|| echo 0` emitted a second zero and stage 3's
  report read `byte-identical to stage 1   0` followed by a bare `0`.
