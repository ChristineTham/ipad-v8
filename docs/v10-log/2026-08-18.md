## Three harness faults, all of which cost a run

- **An unbounded log filled a 120 MB filesystem, twice, at the same unit.**
  `asd`'s `asd.h` includes a `config.h` that does not exist, and the compiler's
  output went to `>> u.log` with no limit. The transcript showed the message three
  times only because the DISPLAY was `sed -e 3q`. Then V10's allocator hid it:
  `lsys/fs/alloc.c` prints `file system full` and **sleeps** waiting for space
  that is not coming, so the run neither progressed nor died — a `vax750` at 100%
  CPU with a kernel message every few seconds. Fixed structurally, with
  `| sed -e 40q`: the pipe closes, the compiler gets EPIPE, and no counting or
  truncation can be outrun. The verdict still uses both tests, with the status
  carried through the pipe as its own line because a pipeline's status is `sed`'s
  and 1985 `sh` has no `PIPESTATUS`.
- **I blamed the image and was wrong.** The first failure was diagnosed as "the
  `.stage1.s2.s3` image's `/usr` is full because it carries four toolchain installs
  and two object trees", and the default was moved to `.stage1`. `tools/v10-free.py`
  then measured `/usr` at **111.8 MB free** the whole time. That tool exists because
  no guest-side probe can work here — a probe blocks in the same `alloc()` sleep as
  the thing it guards — and it counts the BITMAP rather than trusting `s_tfree`,
  which `alloc.c` sets to 0 on failure under Bell Labs' own commented-out line
  reading *"but it would be wrong FIX"*. Self-validating three ways: `struct filsys`
  computes to exactly one 4096-byte block, `s_fsmnt` reads `/mnt2` and `/mnt`, and
  the popcount matches `s_tfree`.
- **A guest script that exits without its end marker strands the driver.** The
  `dd` probe failed (`dd: not found` — the golden lacks it exactly as it lacks
  `ar`, `cmp`, `tail`, `grep` and `wc`), `worldc.sh` exited, and `v10_run` blocked
  for its full 18,000-second timeout with a simulator at 100% CPU and no console.
  CLAUDE.md's rule that a harness must terminate itself now has to hold inside the
  guest too: every top-level exit prints `WORLDC-done`.

And one piece of my own process worth writing down: **`bash tools/norun.sh` is not
a check.** It is a library to source, so running it defines two functions and exits
0 silently, which reads exactly like a pass. I used it as a check repeatedly. The
real guards were working throughout — `v10-srcdisk.sh` refused with *"norun: a
simulator is already running (pid13727)"* and `v10-compile.sh` refused on a stale
srcid — while I read a 42/42 out of the previous run's log file and believed a
rebuild had happened. No overlap occurred and nothing was corrupted. The guards
were right; the monitoring was sloppy.

## `ar` bundles source as well as objects, and it caught me twice

The load-bearing finding, now a CLAUDE.md gotcha. `ar` predates `tar` being
everywhere and was the ordinary way to package any file set, so on this tape a
`.a` is **not** evidence of a link library. Only the naming distinguishes them:
**`X.c.a` holds `.c` files; `libX.a` holds `.o` files.** `libplot/libpen/`
carries both — `libpen.a` (21 objects) and `pen.c.a` (22 sources).

It is not a curiosity. It is the tape's own designated build route for the whole
libplot family, in every one of those makefiles:

	lib4014.a: tek.c.a
		mkdir xplot
		cd xplot;ar x ../tek.c.a
		cd xplot;cc -c -O *.c
		cd xplot;ar rc ../lib4014.a *.o

So `ar x` is step one of the recipe. Three consequences that all read as tape rot
until the mechanism is understood:

- **`libtr`'s archive has 30 objects and its directory has 6 `.c` files.** The
  other 24 are inside `tr.c.a`.
- **Four libraries have their only source in a bundle** — `lib2621`, `libblit`,
  `libram`, `libplot` — so a survey that reads directories finds them empty and
  concludes `-lplot` cannot be built. It can.
- **The headers are bundled too.** `hp.h` in `hp.c.a`, `ram.h` in `ramtek.c.a`,
  `jcom.h` and `jplot.h` in `blit.c.a` — 143 of the 145 apparent header blocks
  were these four, sitting in the very archive the recipe unpacks.

Three more shapes in the same family, each of which also reads as breakage:

- **Two `lib*.a` are not archives at all.** `libdbm` is `mv dbm.o libdbm.a`;
  `libsdb` is `as dbxxx.s -o libsdb.a`. `ld` accepts them because it reads the
  magic number, not the suffix; `ar t` and `ranlib` do not.
- **An archive's name need not match its `-l` flag.** `libtermlib` builds
  `termcap.a`, installs it as `libtermcap.a` and hard-links `libtermlib.a` to
  that — one build answering two flags and matching neither its directory nor its
  product. `libcurses` calls its archive **`crlib`**. `libl` builds `libl.a`
  beside a prebuilt `libln.a`.
- **`libF77/mkfile` names `CC = lcc` while `libI77/mkfile` names `CC = cc`.**
  Sister libraries, two compilers — libc's mixed toolchain again, now at library
  granularity rather than per member.

## Five faults in my own survey, four of them pessimistic

Every one was caught by a check rather than by review, which is the only reason
they are listed as history and not as results:

- **`includes_of` returns `(bracket, header, guard)` and I unpacked
  `(header, bracket, depth)`** — so every lookup asked the resolver for a header
  literally named `"`, and 35 of 362 members "resolved". Same family as the
  fixpoint's *seven differences from zero comparisons*, where `v10_order`'s one
  column was destructured as rows. **K10.1's three faults all ran the flattering
  way**, which is what its `sanity()` was built to catch; this one ran the other
  way and slipped straight through, so the check is now two-sided.
- **`WORLD.sources()` answers `.c/.h/.s`**, so `curses.h` and `curses.c` both
  became `curses.o` and the report printed **363 members resolving out of 362** —
  a total larger than its own subtotal. Asserted now, not printed.
- **`${OBJS}` and `${AR}` went unexpanded** (only `$(...)` and `$...` were
  handled), so libcurses' archive target `crlib` was invisible and the library
  was classified `single`: one object, `ranlib`-blessed, failing only at link
  time. `single` with more than one member is now a contradiction the tool
  refuses.
- **mk's `$L(bdelete.o)` member syntax was unread** — the same idiom libc's
  mkfile uses — so `libcbt` (17 uses, the fourth highest demand) fell through to
  a glob giving 14 members where the mkfile says **8**.
- **A literal `*.o` and an `ar` padding slot were counted as members**, from
  `libplot/libplot`'s `ar r libplot.a *.o` and `netfs/libnetb`'s
  `__________EBEB_`. Both read as members with no source, which looks like a gap
  in the tape and is a gap in the parser.

## And three bugs in the guest script, found by re-reading before the run

- **`sed -e 1q -e 's/ .*//'` prints the whole line.** sed applies commands in
  order per line and `q` **auto-prints before quitting**, so `1q` fired first and
  the substitution never ran: `one` came out as `dbm.o dbm.c`, `test -s` failed,
  and `libdbm` and `libsdb` would both have reported unbuildable for no reason.
  Substitute first, quit second.
- **The bundle-extraction failure path skipped the per-library verdict**, so a
  library failing there was counted in neither `TALLYB` nor `TALLYF` — and the
  driver compares those against the manifest. A hole in the accounting reads as a
  transcript that lost data, which is the one thing that cross-check exists to
  distinguish.
- **`as` takes the tape's own argument order**, `as file -o out`, per
  `libsdb/Makefile`'s `as dbxxx.s -o libsdb.a`. Matching it removes a guess.

## The first guest run: 26 of 26, and 42 members had not built

`tools/v10-libs.sh` printed this, plainly, without complaint:

	every member compiled         26
	some member did not            0
	members that did not build    42

All three cannot be true. **The headline was withdrawn**, and the driver now
refuses to print when `TALLYM > 0` while `TALLYF == 0`.

**The guest-versus-host cross-check could not see it.** Both instruments read
the same tokens and agreed perfectly about a number that was wrong — *two
readings agreeing is not two readings being right*. What was missing was
**internal** consistency: if any member failed, at least one library must have.

The cause is the shell. The member loop is `while read obj src ... done <
objs.lst`, and the historical Bourne shell **forks for a compound command
carrying an input redirection** — so `echo >> mem.log` survived (a file) and
`nf="$nf."` did not (a variable in a dead child). Every library reached its
verdict with an empty tally. Meanwhile **`ar cr` was handed 42 object names that
did not exist, archived what it could open, and `ranlib` blessed all 26.**

Rule: *in 1970s sh, never carry a tally out of a redirected loop in a variable.*
The tally is a file now, which is immune either way — so the fix does not depend
on the diagnosis being right.

Two assertions were also wrong about a build that was right: `test -s can.log`
asks for a **non-empty** log, and a compile that succeeds writes nothing, so the
canary reported NO while `LCANARY-cc-ok` sat in the same transcript; and stage 2
installs libc to `/usr/s2`, not `/usr/s1`.

## Extending the variant-header decision, and finding that most of it cannot be

`installable()` decides mechanically instead of by eye — it rejects a variant
carrying `extern "C"`, `void *`, `const`, a prototype, an anonymous struct, or an
ANSI `U` suffix. Measured over every copy r70 keeps:

	stddef.h  7 units   lcc/ CC/ olcc/   all parse; lcc's is chosen because
	                                     only lcc's GUARDS its size_t typedef
	limits.h  3 units   lcc/ CC/         both parse; lcc's is right on
	                                     signedness -- CC's INT_MIN is

	u.h       1 unit    olcc/ libc/      olcc's parses; libc's declares an

**The test reproduces all three of stage 2's choices independently**, which is

`CC/stdarg.h` is the one installed — and `INSTALLED_EXTRA` said lcc's for a week
while the machine had CC's, which is exactly the drift the cross-check in
`sanity()` now makes impossible.

## Running yacc and lex, which the survey had skipped

`csources()` takes `.c` files, so nine units were reported
`blocked: missing:y.tab.h` — a header **yacc writes** — and `expr` and `ipa` were
not surveyed at all, because their only source is a grammar. Four things had to
be got right and all four were got wrong first:

- **Four suffixes, not two.** `cmd/ratfor`'s grammar is `r.g` and `cmd/ipa`'s
  lexer is `ipa_trans.lex`; a scan for `*.y` and `*.l` finds neither, and
  ratfor's makefile says `yacc -d r.g` in as many words.
- **A recipe is a BLOCK, not a line.** `cmd/ccom` runs yacc and then `sed`s
  `y.tab.c` into `cgram.c` on the next line; `cmd/2500` edits it with `ed`.
  Judged one line at a time both look like a plain yacc call. A *rename*
  (`cmd/cpp`'s `mv y.tab.c cpy.c`) is not a transform, and the first version of
  the test could not tell the two apart.
- **A tool name in argument position is not a tool being run**: `cc … -o lex` in
  `cmd/lex`, `$(CC) -o yacc y?.o` in `cmd/yacc` and `cmd/picasso`.
- **The object is the generator's natural output, not a name we invent.**
  `cmd/config`'s `OBJS` names `y.tab.o` and `lex.yy.o` outright, and deriving
  from the grammar gave `config.y` and `config.l` the *same* object.

`-d` is the tape's own flag: sixteen makefiles write `yacc -d` outright and four
more write `$YFLAGS` over `YFLAGS = -d`.

Two more costs, both paid in whole runs. **yacc is at
`/usr/s1/usr/bin/yacc`** — `yacc.mk` installs to `$(TOOLDIR)/usr/bin/yacc` —
and written out by hand as `$T1/bin/yacc` it failed for all fifty generator rows
and turned 241 units into 232, which reads as a regression and was a typo. The
path is read from `tc.order` now, which is the file stage 1 installs from.
And **lex needs `/usr/lib/lex/ncform`**, which the golden has no `/usr/lib/lex`
for at all; `ncform` is on the tape beside the lex source, but `world.cpio`
carries only `.c/.h/.s` and grammars, so the install failed one line earlier with
`No such file or directory` and the real failure hid behind the second.

# K10.3 — the world links, and the failures are findings

`bash tools/v10-link.sh` on K10.2's output image. `worldc.sh` takes an optional
DESTDIR and then links and installs, so the compile numbers in K10.1 and K10.3
come from the same lines and a difference between them is a fault in one of the
runs rather than a finding — which is how the 5620-header drift above was caught.

**The install is staged**, under `/usr/w10`, never over the machine's own `/bin`
and `/etc`. Three reasons and the first two decide it: the 46 prebuilt binaries
are the oracle and installing over them destroys the comparison on the only
machine that has both; and V10's `ld` writes its output even when symbols are
undefined, so a bad `/etc/init` would be an unbootable disk — v8's stage 8 built
empty *directories* named `/bin/sh` and `/etc/init` and the disk walked 4,507
files and then stopped dead after autoconfig with the CPU idle. K11 wants a tree
to copy in, which is what this produces.

## A `cmd/` directory is not necessarily a command

**71 of the 358 units carry more than one `main()`.** `cmd/worm` has 22 programs
in it, `cmd/qsnap` 17, `cmd/uucp` 11; `cmd/compact` is the small clear case,
`compact.c` and `uncompact.c`. Linking a unit's objects together fails on
`multiply defined _main`, and the obvious repair is worse than the skip: pairing
each `main` with *all* the unit's other objects would give `cmd/awk` a `maketab`
carrying the whole of awk, because `ld` pulls in every `.o` it is named. Which
objects belong to which program is in each unit's own makefile — which is exactly
why the boot path has generated makefiles. `world.link` names all 71 and builds
none of them, so 281 of 358 units are linkable as one program.

## `gets` WAS DELETED FROM libc BY BELL LABS, ON PURPOSE, IN 1988

Two commands — `clear` and `dired` — compile and then fail to link on
`Undefined: _gets`, and `size` and `file` on `_N_BADMAG` and `_N_STROFF`. The
first pair is the interesting one, and the tape answers it in its own words.
There is **no `libc/stdio/gets.c`**. There is `libc/stdio/gets.c-1`, whose first
lines are:

	/* @(#)gets.c	4.1 (Berkeley) 12/21/80 */
	/*
	 * Deleted from libc.a by td, 88.11.07
	 * gets is an unacceptable security hole.
	 */

`gets.o` is absent from Bell Labs' own `libc.a`, and so are `gtty.o` and
`stty.o`. So these are not commands our build cannot link: **they call a function
CSRC deliberately removed on 7 November 1988**, eleven years before C99
deprecated it and twenty-three before the standard dropped it, and they could not
have linked on the tape's own machine either. Restoring `gets` would undo a
documented security decision — which the authenticity rule settles: the tape is
the specification, including where it is inconvenient.

**The `-1` suffix means two different things in the same tree, and only one of
them is a decision.** `libc/gen/rand.c-1` and `libc/math/hypot.c-1` sit beside a
live `rand.c` and `hypot.c` and are ordinary superseded copies; `gets.c-1` has no
live counterpart and carries the note. Read the file, not the suffix.

## Three faults in this harness, all of them mine, all caught by its own guards

- **The staged root was never created, because the V10 golden has no `sort`.**
  `sed … | sort -u > /tmp/dests` answered `sort: not found`, the destination list
  came out empty, the `mkdir` walk made nothing, and all 281 installs failed —
  eleven assertions saying NO about a tree that was never created, while the link
  half had worked perfectly. The dedup was never needed: `mkdir` on an existing

  with `ar`, `cmp`, `tail`, `grep`, `wc`, `dd` and `find`.
- **The driver died silently between the tally and the report**, because it used
  `set -e`: `grep -oE` exits 1 when it matches nothing, `pipefail` fails the
  whole `c10()` pipeline, and a completed run printed no summary at all because
  `CINSTALL` happened to appear zero times. A counter that cannot count to zero
  is not a counter.
- **The guest and the host disagreed 200 to 0 about installs**, because the
  success path wrote `CINSTALL` to `res.log` and did not echo it — and the host

And one diagnostic that could not diagnose: `cmd/sh` reported `CFAILED` followed

the display is `sed -e 3q` — so a unit with many sources fills those three lines
with the ones that *worked*. Only the failures go in that log now. **A
diagnostic that prints the successes is worse than none: it looks like an

# K10.4 — compile the files the build compiles

The limit K10.3 ran into is not a property of the Tenth Edition: `worldc.sh`
compiled **every** `.c` in a unit's directory, and a unit's directory holds files
its build does not use. `cmd/sh` is the case that matters —

	"cmd/sh/profile.c":18: illegal pointer/integer combination, op =

— and `profile.c` is not among the 24 objects in sh's own `$OFILES`. So the
survey compiled a file the tape never compiles and failed the shell on it.

Fifty units are like that, and what they hold is exactly what a working directory
accumulates: `hello.c` and `x.c`, awk's `maketab` helper, other machines' back
ends in `cmd/gcc` (`output-m68k.c`, `output-ns32k.c`, `output-spur.c`), superseded
generations (`osed0.c`, `olint1.c`, `OLDex_temp.c`), and `2.test.c`. Reading each
unit's own object list is therefore a **fidelity** change and not a way to raise a
number — the tape's build description is the specification.

## Three witnesses, and two guards, because this rule runs in the flattering direction

Dropping a source raises the count of units that compile, so a misreading here
looks like progress. The rule keeps a source when **any** of three things is true,
each of them the tape's own statement:

- its object is named in an object list in the build files (macros expanded, and
  **continuation lines joined first** — sh's `$OFILES` spans three lines and
  reading them separately finds eight of twenty-four objects, which would have
  "proved" that sixteen of the shell's sources are not in its build);
- a leftover `.o` sits beside it — these are developers' working directories, so
  what was compiled in place is evidence of what the build uses, and `cmd/sh` has
  24 objects present with `profile.c` the one source without one;
- the build files **name the source itself**. `cmd/docgen`'s makefile says
  `docgen: docgen.c` and lets make's implicit rule do the rest, so no `docgen.o`
  exists in the text or on disk — and without this witness the two-object test
  dropped the program the unit is named after. It also rescued awk's `maketab.c`
  and lint's `lint2.c`.

Then two refusals, both recorded rather than silent:

- never drop the source carrying a unit's **only** `main()`;
- never drop **more than half** a unit's sources. Past that the likelier
  explanation is that the reader has misread the build than that the tape ships
  that much dead code — `cmd/xref` (4 of 5), `cmd/spool` (6 of 9) and `cmd/style`
  (6 of 8) all sat above the line.

The three witnesses took the drop set from 112 sources across 37 units to **87
across 29**, and every one is listed in `v10/mk/gen/world.drop` together with all
eleven refusals. A rule that quietly declines to fire is indistinguishable from
one that had nothing to do.

**And the host's model follows the guest's behaviour**, which is the lesson
`inc.extra` cost a phase to learn: a dropped source's `#include`s no longer count
against its unit, because the guest will not compile it. Headers are still
scanned — a `.h` is included by whoever includes it, dropped or not.

# K11 and K12 — where the remaining two stand

**K11 is prepared and its arithmetic is settled host-side.** The ceiling being
retired was never V10's: every V10 disk so far was made *by V8*, so it had to fit
V8's in-superblock bitmap, and `MAXSMALL = BITMAP*BITCELL = 961*32 = 30,752`
blocks is exactly the size of every stage image — 120.1 MB, the ceiling itself.
V10's `lsys/sys/filsys.h` has a third union arm, and `cmd/mkbitfs.c` switches to
it unprompted:

	if (size - isize <= MAXSMALL)
		smallfree();
	else
		largefree(fd);

`largefree()` writes the bitmap into the **last** `nblks` blocks of the
filesystem, `nblks = (s_fsize + BITSPERBLK-1)/BITSPERBLK` with
`BITSPERBLK = 4096*8 = 32768`, and refuses only when `nblks` reaches `BITMAP-1`.
So the new ceiling is `960 * 32768 = 31,457,280` blocks of 4096 — **128 GB**, a
thousandfold, and four hundred times the largest disk this project emulates.

`tools/v10-bigfs.sh` and `.exp` build the **tape's** `mkbitfs` (via `mkbitfs.mk`,
which reads `$(SRC)`) rather than our `v10mkbitfs` overlay — that overlay exists
only because V8's `hp` driver reads bit 6 of the minor as part of the drive
number, and on V10 the original check is exactly right. The target is partition
`h`, `ra_sizes[]`'s last entry (`HUGE, 0` — the whole drive), so 111,384 blocks:
456 MB, 3.6× MAXSMALL. And `tools/v10-free.py` now counts an **N-arm** bitmap,
which it previously answered `None` for — the arm K11 exists to create. That
matters because *a full V10 filesystem does not fail, it sleeps*, so the host is
the only place the question can be asked.

**K12's two stated reasons are already discharged, and reading V10's own
`streamio.c` resizes what is left.** `v10/src/lsys/astro/ipnx780.m` configures
`netafs 4` and `netbfs 4` and carries the NI1010; K7 builds that kernel and K9
boots it. So the client is compiled in, with instances, on a machine that runs.
Of the N track's four faults:

- **the hang is already fixed** — V8's `istread()` waited forever for a `M_DELIM`
  that a zero-length Datakit write used to produce; V10's does
  `tsleep(..., PRIBIO, 30)` and returns −1 on `TS_TIME`, behind a parameter whose
  own declaration says *"flag is for timeout debugging"*;
- **the 512-byte stream head transfers** — `strdata` is
  `{ strput, NULL, nilopen, nulldev, 512, 256 }`, the same high-water mark — but
  V10 has a path V8 did not, `if (count >= 512 && stq->wrq->next->flag&QBIGB)` at
  two sites, so a **QBIGB** queue takes big transfers whole. Whether pushing that
  flag suffices is cheaper to measure than patching a constant, and it goes first;
- **the short read and the discarded remainder both transfer** — `istread()`
  returns `nc` whenever a queue momentarily empties without `QDELIM`, and copies
  `min(count, wptr-rptr)` before freeing the block either way.

The userland is better than V8's: `src/netfs/` ships `libnetb` (K10.2 already
builds and installs it), `serv/zarf` to present a local filesystem, and
`runfs`/`setup` to start and supervise servers, where V8 had only the client.
Sequenced honestly, K12 is a phase and not a run — the N track was N0–N7 for the
same ground on V8.

# K11 — THE CEILING WAS V8'S, and V10 removed it in one run

`bash tools/v10-bigfs.sh` — **20/20 in the guest, exit 0**, and the host reads off
the disk V10 wrote:

	filesystem size   111384 blocks   435.1 MB
	i-list              1024 blocks
	s_tfree (a HINT)  110311 blocks   430.9 MB
	bitmap valid=1 flag=1
	FREE BY BITMAP    110311 blocks   430.9 MB   <- read from the last 4
	                                                blocks of the filesystem

`flag=1` is the whole result: the free-block bitmap is **outside the superblock**,
in the N arm of `filsys`'s union — the arm V8's `filsys.h` does not have. 111,384
blocks is **3.6× the 30,752** that every previous V10 disk stopped at, and the two
free-space figures agree exactly while coming from completely different places:
`s_tfree` is a counter the kernel maintains and the 110,311 beside it was counted
bit by bit out of four bitmap blocks at the end of the volume. That agreement is
the confirmation that the reader is looking where `largefree()` wrote.

V10 then mounted it, wrote to it, unmounted it, **remounted it**, and found both
files — which is the assertion that matters, because it is the one that proves the
bitmap reached the disk rather than only living in core.

## Four of the twenty assertions could not fail, and the fifth wrote to the wrong disk

The first run reported 14/17 with three passes that were incapable of failing, and
the pattern is the one this project keeps meeting: an assertion phrased as
*something happened* rather than *the thing I want is true*.

- **`ls X && echo OK` is not an existence test on V10, because `ls` exits 0 for a
  file that does not exist.** `cmd/ls.c` calls `perror()` on the stat failure and
  falls through to `exit(0)`, so the node assertion passed while `mknod` had never
  run — the golden has no `/etc/mknod` at all (`mknod: not found`; add it to `ar`,
  `cmp`, `tail`, `grep`, `wc`, `dd`, `find` and `sort`). `test -b` is the real
  question and `cmd/test.c` has it.
- **`icheck /dev/... ; echo OK` prints OK whatever icheck does.** A semicolon where
  `&&` was meant, and it duly reported "icheck reads it back: ok" directly above
  `cannot open /dev/ra2h`.
- **A write test after a failed mount writes to the mount point's own directory
  and passes.** `/big` was an ordinary directory on the root filesystem, so "and
  writes to it" and "both files are still there" both said yes about a filesystem
  that did not exist. Everything downstream of the mount is gated on the mount
  now, and a skipped assertion is reported as a failure — a phase that did not run
  is not a phase that passed.

And then the instructive one. **The second run passed all nineteen guest
assertions while writing the filesystem onto the source disk.** The minor was 79:

	64 | (1<<3) | 7  =  79        UNIT(79) = (79>>3)&07 = 1

so the node named `ra2h` addressed **unit 1** — the courier disk — while the blank
was attached as `rq2`. The comment above it even read *"unit 1, the blank disk"*,
contradicting the attachment three lines up. mkbitfs made a perfectly good
111,384-block filesystem, V10 mounted it, wrote to it, unmounted and remounted it,
and every assertion was true; only the host's read of the blank image, still all
zeroes, said otherwise. The right minor is **87**.

Two things to keep from that. **The clone rule is what saved it** — the disk the
guest destroyed was `.k11src`, and `ipnx-v10-src.img`'s own stamp still matched
the repo afterwards. And *a guest can report success about the wrong disk*, which
is the argument for the host-side check being the decisive one; the harness now
also re-reads a file off the courier mount immediately after `mkbitfs`, which
would have caught it in the guest.

The block major was the one number that did not need debugging, because it was
measured rather than assumed: `/dev/ra0a` and `/dev/ra0c` print `7, 64` and
`7, 66` — `BITFS|unit0|part0` and `BITFS|unit0|part2`, the same arithmetic on
nodes Bell Labs made.

## And one host-side check was too strict for the thing it exists to check

`v10-free.py` refused the new superblock with *"s_fsmnt does not begin with a
printable byte"*. It was reading it perfectly: `s_fsmnt` is the mount point, and a
filesystem that has never been mounted has none, so a fresh `mkbitfs` writes
zeroes there. Every image the tool had seen carried `/mnt2`. A NUL is a legitimate
empty string; anything else non-printable is still the offsets being wrong.

# K12.0 — NETFS RUNS ON V10, and the remaining work is transport only

`bash tools/v10-netfs.sh` — **16/16, exit 0.** A netfs filesystem mounted on V10,
served by V10's own `zarf`, with **no network in it at all**:

	# ls /n/local
	adm bin blit include jerq k10lib k12obj lib obj s1 tmp

	# sed -e 2q /n/local/include/stdio.h
	#define BUFSIZ 4096
	#define _NFILE 120

	# cmp /n/local/include/stdio.h /usr/include/stdio.h      -- byte-identical
	# cp /etc/motd /n/local/tmp/nbprobe                      -- and it writes

K12 was scoped as a phase — kernel stream work, a transport, then a mount — and
this run puts the decisive measurement first, the way B1 and B2.0 were won. V10
ships the means: `netfs/README` says *"runfs starts a server by hand, mounted on
some local file and connected through a pipe"*, and `runfs.c` does exactly that —
`pipe()`, `fork()`, the child runs the uid/login handshake and calls **`fmount(fd,
…)`** while the parent `exec`s the server. `fmount(2)` is one of the six syscalls
V10 has and V8 does not, and it mounts on a **file descriptor**: no device node, no
Interlan, no TCP, no line discipline.

So the two halves of K12 separate cleanly, and the answer is now known: **the
client, the netb protocol library and the mount all work.** Everything left is
transport — the NI1010 at `0764000 vec 0350`, a stream discipline under it, and
the same `fmount` call on a socket instead of a pipe.

**The kernel had to be ours and only one image has it.** `seki` configures
`netbfs 0` — the filesystem type compiled in with zero instances — so the golden
cannot mount one however good the userland is. `ipnx780.m` configures `netafs 4`
and `netbfs 4`; K7 builds that kernel and K9 boots it. This runs on **K7's output
built on top of K10.2's** (`bash tools/v10-kernel.sh
ipnx-v10-ra81.img.stage1.k102`, 17/17), so `/usr/lib/libnetb.a` is there too —
stages chain that way throughout.

## The tape's makefile picks the System V directory reader on a Research Unix tree

`serv/` ships **three** directory readers and `serv/makefile`'s `ZFILES` names the
wrong one for this machine:

	libdir.c     #include <dirent.h>     System V -- and r70 has NO dirent.h
	bsdlibdir.c  #include <sys/dir.h>    BSD
	resdir.c     no directory header at all

so the build died on `libdir.c: 16: Can't find include file dirent.h`. `resdir.c`
is the one, and it says so itself: *"read directories, research-style / uses
dirread system call, which does just what we want"*. **`dirread` is V10 syscall
22** — the slot V8 fills with `sumount` — with `libc/sys/dirread.s` as its stub, so
it is a call V8 does not have and V10 does. `resdir.c` defines `dodirread()` and
`dodircleanup()`; `libdir`'s third function, `ftod()`, is `static` and internal, so
it is a complete drop-in at 33 lines against 104.

This is the `libc/mkfile names cc for members only lcc can compile` finding again,
in a different subsystem, and it earns the general rule another outing: **no
makefile on this tape is a reliable guide to which of its own files belongs to this
machine.**

## Two more assertions that could not fail, and one verdict that contradicted itself

- **`cat /etc/mtab` was asserted to show the mount, and a netfs mount is not in
  mtab.** `/etc/mtab` is written by `mount(8)`, and `runfs` never calls it — it
  calls `fmount(2)` directly. Exactly the same shape as V8, where a netfs mount is
  a `gmount(2)` object released by `nmount -u <id>` and `umount(8)` knows nothing
  about it. The assertion was asserting something untrue; it is now printed for the
  record and the mount is proved by *using* it.
- **`test -s $MP/lib/libc.a` named a file that does not exist** — `libc.a` is in
  `/lib`, not `/usr/lib` — so it was false about the tree rather than about netfs.
  Its replacement, `sed -n '$=' … libnetb.a`, produced no output and no error
  either: counting lines in a binary archive is a test artefact. What it finally
  became is the strongest read test available here, and one the loopback makes
  possible: **`cmp` the same file read through netfs against read locally.**
- And the driver printed *"the pipe mount did NOT work"* over a transcript showing
  the mount working, because its verdict keyed on the run's exit status rather than
  on the decisive assertions. **A summary that contradicts its own evidence is
  worse than none.** It counts the three that decide the question now.

That is six unfailable assertions across K11 and K12, in three shapes — a
semicolon where `&&` was meant, a command whose exit status does not mean what it
looks like, and a test whose subject does not exist so it tests something else.
CLAUDE.md carries them as one discipline now.

## K12.1 — the transport, first two attempts, and four things read rather than run

Two runs, 7/15 then 9/15, and every one of the six named causes was found by

### `tcpconfig` was not on the courier disk, and `libs.cpio` is why

`ipc/internet/` holds the whole inet userland — `ipconfig`, `tcpconfig`,
`udpconfig`, `route`, `netstat`, `arp`, `gettable`, as source *and* as Bell Labs'
own 1995 VAX binaries — and the source disk carries `ipc/libin` and `ipc/libipc`
because those are two of K10.2's twenty-six **libraries** and stops there. So the
assertion `tcpconfig is present` failed about a file that had never been copied,

### `dipconfig` is the `ipconfig` that needs no twenty-seventh library

The mkfile's own two link lines are the whole argument:

	ipconfig:  cc -o ipconfig  ipconfig.o  $LIBIN $LIBCOMMON
	dipconfig: cc -o dipconfig dipconfig.o $LIBIN

`libcommon` is `ipc/mgrs/common/` — `logevent`, `logconsole`, `detach`, `print`,
`fprint` — in no manifest, wanted for a program whose extra features over
`dipconfig` are a subnet mask and a syslog. `dipconfig` is the earlier generation
of the same program, does the identical five ioctls (`FIOPUSHLD ip_ld`,
`IPIOLOCAL`, `IPIOHOST`/`IPIONET`, `IPIOARP`, `ENIOTYPE`), and needs only what
K10.2 built. And `tcpconfig` has **no rule in that mkfile at all**
(`MGRS=ipconfig routed dkipconfig udpconfig`) while its prebuilt binary sits in
the directory — the working-directory pattern again, in the opposite direction to
the 46 commands.

`LIBIN` is **two** archives, `../libin/libin.a ../libipc/libipc.a`, and that is
load-bearing rather than decorative. A twenty-line symbol dump over the tape's own
`libin.a` says why in one reading:

	tcp_lib.o undefined externals:
	  __iob _close _errno _errstr _flabclr _fprintf _in_address
	  _in_service _open _perror _read _sprintf _strlen _write

`_errstr` is `libipc/ipcopen.c` and `_flabclr` is `libc/sys/label.c`; `in_address`
itself calls `qvalue()` from `libipc/qns.o` for the not-a-dotted-quad case. **An
archive member's undefined externals name the other archives you need**, and
reading them beats discovering them from a failed link.

### `nafsmnt` failed on Bell Labs' header, and the fault was ours

	"/usr/include/sys/inet/tcp.h":3:illegal type combination
	"/usr/include/sys/inet/tcp.h":5:illegal type combination

Lines 3 and 5 are `typedef unsigned short tcp_port` and `typedef unsigned long
tcp_seq`, which reads as pcc2 rejecting `unsigned short` — contradicted by every
other file in the tree. `tcp.h` has no include guard and `tcp_user.h` includes it
itself under `#ifndef KERNEL`, so naming both gives the compiler the typedefs
twice, and the second time `tcp_port` is already a type name: three type
specifiers combined. `<sys/inet/in.h>` escaped only because its first line happens
to be `#ifndef INADDR_ANY`. Two errors pointing at a 1983 header, none at the file
that caused them — and the tape's own idiom is one header, `ipc/libin/tcp_lib.c`
including `<sys/inet/tcp_user.h>` and nothing else.

While there, `nafsmnt` stopped hand-rolling the odd-minor loop and the tcpuser
exchange and calls libin's `tcp_sock()` and `tcp_connect()`, which are what Bell
Labs wrote for exactly this caller — `tcp_connect` sets `code`, writes the struct,
reads the reply back into the same struct and decodes every `TCPC_` value into
`errstr`. Hand-rolling it is how the reply structure came to be written as V8's in
the first place.

### The majors are the tape's, not our config's — `lsys/lib/tab`

The obvious reading of a generated `cdevsw[]` is that it follows the config's
device list, in which case every node in `v10/mk/gen/proto-dev` (majors taken from
`seki.c.c`) would be wrong under `ipnx780`. It is not so: `lsys/lib/tab`, the `-t`
argument K7 already passes to `mkconf`, is a **fixed** assignment —

	cdev 42 ip   cdev 43 tcp   cdev 44 ni1010a   cdev 50 udp
	ld 0 ttyld   ld 10 ipld    ld 11 tcpld       ld 14 udpld

— so `il` is char major 44 on any V10 kernel, `/dev/ip6` and `/dev/ip17` are IP
**protocol numbers** (6 = TCP, 17 = UDP, exactly what V8's `/etc/rc` pushes onto
them), and the `ld` indices match `libc/gen/linedis.c`'s table, whose four inet
numbers are the same integers V8 uses.

That also retires a worry the config itself raises. `ipnx780.m` carries `ipld 0 /
udpld 0 / tcpld 0`, copied from `alice.m`, and after `netafs 0` really having meant
no netfs, a zero there reads as no TCP. The counts are different animals — a
filesystem type needs instances, a line discipline needs a `streamtab[]` slot — and
**the tarball ships mkconf's own output for eight machines**: `lsys/misc/europa.m`
has all three at zero and `europa.c.c` beside it still says `&ipstream /* 10 */`,
`&tcpstream /* 11 */`, `&udpstream /* 14 */`. When the question is "what would the
generator do", read one of its outputs instead of running it.

### And the Interlan is at the wrong address, by 040

The one thing here that is a genuine mismatch rather than a misreading, found
before the run that would have shown it as `dipconfig` failing to open
`/dev/il0`. `ipnx780.m` says `ni1010a 0 ub 0 reg 0764000 vec 0350` — alice's own
numbers, and four of Bell Labs' six configs agree on 0764000 while three say
0164000. `libsimh/patches/apply-il.sh` puts the card at I/O-page offset **04040**,
which is 0764040 in the notation V10's config uses, because 0164040 is what V8's
kernel declares and what `dev/il.c`'s `ilstd[]` calls the board's standard
address. The same patch marks the vector `flt VEC`: V8 discovers it in `ilprobe`
through `cvec`, and V10's `mkconf` compiles 0350 in.

So there are two numbers to reconcile and only one of them looks like a mismatch.
The Unibus-to-SIMH mapping needed for either is a measurement rather than a
header — the UDA50A appears as SIMH `2013F468` while the config gives it Unibus
`0772150`, so `IOPAGEBASE` is `0x20100000` and Unibus 0764000 is SIMH `2013E800`.
The harness sets the simulator's address to that, which is this project's stated
preference where the two disagree (it keeps V10's numbers and leaves V8's working
path alone, which editing the shared patch would not), and **measures** the vector
with `show il` beside `show rq` — because `rq`'s vector is one the config gets
right, so its SIMH notation is what settles how 0350 has to be written.

### What the stream layer will need, decided by reading before measuring

`lsys/fs/neta.c` calls `istwrite`/`istread` exactly as V8's netafs does (lines
639–662), so the N track's four stream faults are the right list to check. Three
of the four **do not transfer**, and the one that does is not the one the plan
named:

- **The EOF hang is fixed.** V8 waited for an `M_DELIM` that a zero-length Datakit
  write used to produce; V10 writes `tsleep((caddr_t)RD(stq->wrq), PRIBIO, 30)`
  and returns −1 on `TS_TIME`. A bounded failure instead of a hang.
- **The 512-byte stream head is already handled on this path.** `strdata` is still
  `{ …, 512, 256 }`, but `istwrite` takes a 1024-byte block when
  `count >= 512 && stq->wrq->next->flag&QBIGB` — and `stq->wrq->next` for netfs is
  the **tcp device's** write queue, which `lsys/inet/tcp_device.c:96` sets QBIGB on
  in `tcpdopen`. Its `qinit`s are `{…, 2048, 64}` both ways, four times the head's.
  So QBIGB — which the plan named as the first thing to try — is already on.
- **The short read does transfer, and QDELIM is why.** `istread` returns early when
  `nc && (OTHERQ(stq->wrq->next)->flag&QDELIM)==0`, i.e. when the queue momentarily
  empties and the downstream read queue does not promise delimiters.
  `tcp_ld.c`'s `tcpopen` sets `QDELIM` on **both** its queues; `tcp_device.c`'s
  `tcpdopen` sets `QBIGB` and **not** `QDELIM`. By the tape's own pattern that is
  an omission rather than a decision — `ni1010a.c:141`, `deqna.c:202`,
  `kdi.c:177` and `debna.c:90` all write `QDELIM|QBIGB` together. One line, in the
  overlay, with that as the stated reason.
- **The discarded remainder transfers unchanged.** `n = min(count, bp->wptr -
  bp->rptr)` and then `freeb(bp)` regardless, so a block longer than the caller's
  buffer loses its tail. This is the one genuine V8-style fix still needed.

So the order is QDELIM first and the remainder second, and QBIGB not at all —
which is worth stating plainly because the plan had QBIGB first on the argument
that it was cheaper to measure than a constant. Cheaper still was reading who
sets it.

### The three new opcodes are `nami` FLAGS, not commands — so the wire is unchanged

`neta.h` gains `NSEARCH 0`, `NMKDIR 17`, `NRMDIR 18` over V8's, which reads as
three new requests our server would not answer. It is not: `struct senda`'s third
byte is `char flags;  /* now only for nami */`, and V10's `neta.c` uses all six of
`NSEARCH NDEL NLINK NCREAT NMKDIR NRMDIR` as **`x.flags`** beside `cmd = NNAMI` —
lines 419–439 — never as `x.cmd`. The `cmd` values it actually sends are
`NGET NNAMI NPUT NREAD NSTAT NTRUNC NUPDAT NWRT` plus `NSTART`, which is V8's set
exactly. And `NSEARCH` being **0** means a plain lookup is byte-identical to V8's
`flags = 0`.

The one direction that matters in reverse is already right: `neta.c:483` reads
`if(y.flags == NROOT)` to detect having walked out of the mounted filesystem, and
`netfs/Sources/NetFS/Server.swift:280` sets exactly that (`if isRoot { y.flags =
Op.root.rawValue }`). So nothing in the Swift server needs changing for V10, and
`NMKDIR`/`NRMDIR` are wanted only by `mkdir`/`rmdir` — not by a mount, a read or a
write. **The protocol half of K12.1 was already finished by the N track; only the
transport is open**, which is what K12.0 concluded and this confirms one layer
further down.

### The V10 kernel is an `lcc` build, and `asm.sed` is a peephole inliner

Found while costing K12.2, and it changes what a kernel source change means here.
K6/K7 compile only two files — the generated `conf.c` and `low.s` — and link
against **prebuilt archives** in `lsys/lib/`, so `lsys/inet/tcp_device.c` is not
compiled by our kernel build at all. `ar t` places it exactly:

	inet.a   tcp_device.x, tcp_ld.x, the whole ip/udp/tcp stack
	os.a     streamio.x, and the rest of the OS
	fs.a     neta.x, netb.x, fs.x, alloc.x

The members are `.x` (C) and `.z` (assembly), and `lsys/inet/mkfile` gives the
rule:

	%.x: %.c
		lcc $CFLAGS -S $stem.c
		sed -f ../lib/asm.sed <$stem.s | as -o $stem.x

**All six kernel `mkfile`s name `lcc`.** So the mixed-toolchain finding this
project has been recording for libc and the commands extends to the kernel, and
the kernel is the ANSI half — which matters because the prebuilt `etc/lcc` is the
one that emits **empty objects and exits 0** (`bowell.c` hands `-undef` to a cpp
that rejects it).

But the `sed` is the interesting half, and it is **not** an lcc quirk. `asm.sed`
is a peephole inliner over the generated assembly:

	calls $n,_spl6    ->   mfpr $18,r0 ; mtpr $0x18,$18
	calls $n,_splx    ->   mfpr $18,r0 ; mtpr (sp)+,$18
	calls $n,_bcopy   ->   movc3 8(sp),*(sp),*4(sp) ; addl2 $12,sp
	calls $n,_copyin  ->   jsb _Copyin ; addl2 $12,sp

So `spl6()`, `splx()`, `mfpr()`, `bcopy()`, `copyin()` and `resume()` are written
as ordinary C calls throughout the kernel and become inline VAX instructions
afterwards — 1985's inline assembly, done with `sed`. It matches `calls $<n>,_<name>`,
which is the standard VAX calling sequence **any pcc-derived compiler emits**, so
there is a real prospect that `cc` can stand in for `lcc` for a single object.

Consequences for K12.2, all of them cheaper than they looked:

- The patch is one line in `tcp_device.c`, then `-S`, then `sed -f asm.sed`, then
  `as`, then `ar r inet.a && ranlib`, then K7's link. No full kernel source build.
- Skipping the `sed` fails **loudly** — `Undefined: _spl6` at link — which is the
  best kind of precondition.
- Whether `cc` suffices is a measurement, not a guess, and the oracle is on the
  tape: compile one unchanged member both ways and `cmp` against the archive's own
  `.x`. That is the same which-compiler test stage 2 already runs on libc.

### Two faults on the way, and both were on OUR side of the wire

**The IL vector floats and the address was 040 out.** `set il address=2013E800`
took (`show il` prints a `*` for a set value), and the same `show` reported
`vector=C8-CC` against the `0350` `ipnx780.m` compiles in. `show rq` was the wrong
control -- an MSCP controller has "no vector" because the driver hands it one at
initialisation, so the UDA50's `vec 0154` says nothing about notation. The right
control was already recorded: *"dz11 0 vec 0300, SIMH's DZ vector base (C0)"*,
which fixes the mapping as plain octal-to-hex of the same number. 0350 is 0xE8.
The `C8-CC` **range** is explained too: `il_rint_ack` returns `il_dib.vec` and
`il_cint_ack` returns `il_dib.vec + 4`, so the config names only the base.

**`dipconfig` hit the `mv.c` trap in reverse**, and the pattern predicted which
file would break. `sys/param.h:131` is `#include "sys/types.h"`, `types.h` has no
guard, and `dipconfig.c` names both, so all fourteen typedefs parse twice -- with
every error pointing at Bell Labs' header and none at the file that caused them
(`":39: saw TYPE"` is `typedef long daddr_t`; `":44: saw ["` is
`typedef long label_t[14]`). `mv.c` had to *gain* param.h; this had to *lose*
types.h. And `dipconfig` has a mkfile rule and **no prebuilt binary**, exactly
like `mv.c` and `fsck.c`: what will not compile is what nobody had compiled in
place.

### And V10's client fakes the root, which our server had to be told

The mount succeeded and `ls /n/host` said *No such file or directory* while the
server logged six requests it had answered correctly -- `NSTAT ino=2` → errno 2,
then four `NNAMI`, then `NPUT`. The cause is in Bell Labs' own comment,
`lsys/fs/neta.c`'s `nadomount()`:

	/*
	 * fake the root, rather than sending NAGET now,
	 * to avoid a deadlock when a server mounts itself
	 * the next stat will correct it
	 */
	rip->i_un.i_tag = (flag<<16)|ROOTINO;

V8's client opens every mount with `NGET(dev, ROOTINO)`, which is what allocates a
tag in `netfs/Sources/NetFS/Export.swift`. **V10 deliberately skips it** and
synthesises a tag out of its own namespace, and `nastat()` copies `mode`, `nlink`,
`uid`, `gid`, `size` and `tm[]` out of the reply and **not** `y.tag` -- so it keeps
that tag for the life of the mount. `Export.handle(tag:orRootIno:)` now binds the
root handle to the client's tag, narrowly: only `rootIno`, and only when the tag
is unknown, because an unknown tag on any other inode really is a protocol error.

**Also settled: `fmount`'s fourth argument is the DEVICE NUMBER, not a flag.**
`namount(sip, ip, flag, mnt, fstyp)` passes it to `nadomount`, which does
`pi.i_dev = flag; iget(&pi, flag, ROOTINO)` and builds the tag as
`(flag<<16)|ROOTINO`. V8 passed dev as `gmount`'s second argument; V10 moved it to
the last. `nafsmnt.c`'s comment said "fmount keys on the fd, not on this" and that
was wrong.

### What is left is one measured line of kernel

	# ls /n/host
	neta: read -1 expected 48

The kernel's own diagnostic, and it is the fault predicted from reading before any
of this ran: `istread()` copies `min(count, ...)` and then `freeb(bp)` regardless,
so the reply header's read discards the payload sharing its block and the second
read times out. Fixed in the overlay as `lsys/os/streamio.c`, on V8's proven
model. **QDELIM is not what bit** -- the header read succeeded -- but the

reachable on a larger transfer.

`ar r os.a streamio.x` and `ar r inet.a tcp_device.x` plus a relink, not a kernel
source build.

### And pcc does not nest comments, which cost the run in between
