# 2026-08-16 — B1 opens, and the plan turns out to be wrong

*First session of Track B. The intent was to start the cross-build described in
[v10-restoration.md](../v10-restoration.md): import the source, then build a V10
toolchain from it with V8's 1985 `cc`. Two hours in, the plan was retired —
not because it failed, but because it is unnecessary.*

## What was actually in the tarball

`tools/v10-import.py` unpacks `v10src.tar.bz2`, `v10blit.tar.bz2` and
`r70include.tar` into `work/v10/` (`src/`, `blit/`, `include/`), classifying
every file by its first four bytes. **25,682 files** — 25,346 of them before
the include tree was added later in the session:

| kind | count | what it is |
|---|---|---|
| text | 22,315 | source, makefiles, documents, headers |
| object | 1,525 | VAX a.out **0407** |
| binary | 1,209 | fonts, images, data |
| **exec** | **483** | VAX a.out **0410/0413 — linked, runnable** |
| archive | 150 | `ar(1)` |

The `exec` row is the finding. Both this repository's docs and
[RESEARCH.md](../../RESEARCH.md) §7 have said since they were written that V10
"survives as a source-only snapshot … no binaries, no boot media", and the
first half of that is false. Among the 483:

	src/cmd/ccom/vax/comp     340,498 B   the V10 C compiler
	src/cmd/as/as              57,203 B   the V10 assembler
	src/cmd/adb/vax/hello      11,215 B   hello, world -- already linked
	src/cmd/lcc/gen2/vax-v9/rcc 304,392 B lcc, ANSI, targeting V10 VAX
	src/cmd/make/make          50,624 B
	src/libc/libc.a           169,296 B   V10 libc: 262 members, with __.SYMDEF

"No boot media" remains true, and that is the part that matters for B3. But
the toolchain is not missing. It was sitting in the tarball the whole time,
and nobody looked — understandably, since the tarball is 243 MB of a system
nobody could run.

`v10/MANIFEST` records all 25,346 with size, mode and sha256, so this is
re-derivable rather than a claim, and `--verify` re-checks it in about fifteen
seconds.

## The question that follows

If V10's own compiler runs on a V8 kernel, there is no cross-build. So:
**does a 1995 Tenth Edition binary run on a 1985 Eighth Edition kernel?**

The static evidence said probably. Comparing `v8/usr/sys/sys/sysent.c` plus
`vmsysent.c` against `work/v10/src/sys/os/sysent.c` — 129 slots against 128 —
**111 hold the same call at the same index**. Every call a compiler makes is
among them: open 5, read 3, write 4, close 6, creat 8, unlink 10, break 17,
stat 18, seek 19, dup 41, pipe 42, exece 59.

The eighteen that differ are mounts, credentials, reboot — and slot 11, where
V8 kept V7's vestigial `exec` and V10 put a 64-bit `lseek`. Nothing in a
compiler calls slot 11.

But a syscall table is not an ABI: `struct stat` could have grown, `crt0`
could want a different stack, the a.out header could carry a field V8 rejects.
None of that shows in a diff. So the question got an experiment.

## The experiment

`tools/v10-probe.sh` — two netfs servers (the V10 tree read-only at `/n/v10`,
a scratch directory read/write at `/n/t`), a **clone** of the golden, and
`tools/v10-probe.exp` driving the guest.

Serving the tree instead of copying it is itself a change of plan. B0 sized
the tree at 243 MB against a 88 MB `/usr` and concluded that "selective ingest
is mandatory, not merely preferable" — two courier-disk loads for the B1
subset alone. netfs (B0.5, N5–N7) removes the constraint completely: nothing
is copied to guest disk, so the whole tree is reachable and the subset does
not have to be chosen in advance.

Results, first run:

	mount /n/v10                 ok
	mount /n/t                   ok
	V10 hello runs               ok      <- hello, world
	V10 as assembles             ok
	V10 ccom compiles            ok
	V10 crt0 assembles           ok
	V10 as output assembles      ok
	links with V8 ld             NO
	the linked program runs      NO

**A 1995 V10 binary ran on the 1985 V8 kernel on the first attempt**, and so
did V10's assembler and its C compiler. `comp` turned this

```c
char msg[] = "V10-COMPILED-AND-RUN\n";
main() { write(1, msg, sizeof msg - 1); return 0; }
```

into VAX assembly:

	.stabs	"vaxpcc2",0xf0,0,17665,1786890164
	_main:
		pushl	$21
		pushl	$_msg
		pushl	$1
		calls	$3,_write

**`vaxpcc2` is not a V10 marker — do not read it as one.** It looks like a
signature and it is not: V8's `/bin/echo`, off our own golden disk, carries the
same string, because both editions' `ccom` descend from pcc2 and stamp the same
name. Provenance has to come from where the binary was built, not from
grepping it.

## The one failure, which was ours

	ld:v10libc.a: warning: table of contents for archive is out of date;
	              rerun ranlib(1)
	Undefined:
	__cleanup
	__exit
	cerror

Not a V10 problem and not an incompatibility. V8's `ld` reads an archive in a
single sequential pass unless `__.SYMDEF` is *current*, and current means not
older than the archive — so `cp`, which gives the copy a fresh mtime while the
member keeps its 1995 one, demotes a perfectly good table of contents to a
stale one. `cerror.o` sorts before `write.o`, so one forward pass is already
past it when `write.o` asks.

CLAUDE.md has stated the rule since S5: *any rule that copies an archive must
re-`ranlib` it at the destination*. It reads as a V8 build detail and is
nothing of the kind — it applies across the edition boundary for exactly the
same reason it applies within one. The probe now runs `ranlib` after the copy.

Worth recording separately: V8's `ld` parses V10's `__.SYMDEF` correctly.
Parsed host-side against `v8/usr/include/ranlib.h`, the archive yields 421
symbols with sane names — including `_strtol`, `_vfprintf` and `_memmove`,
three of the seven functions [v11-plan.md](../v11-plan.md) lists as missing
from V8's libc and expects `libcompat` to supply. V10's libc has them.

## What this changes

The bootstrap chain in [v10-restoration.md](../v10-restoration.md) had four
links before a V10 program could be compiled. It now has one, and it is not a
cross-build:

	V8 kernel + V10's own comp/as/libc.a  ->  V10 programs

V10's `cc.c` and V8's `cc.c` are the same program eight years apart — same
passes (`/lib/cpp`, `/lib/ccom`, `/lib/c2`, `/bin/as`, `/bin/ld`,
`/lib/crt0.o`), same `-B` prefix, same `-t` pass selection. So the hermetic
`-B` seal built for S5, to stop V8's build reaching into the running system,
is exactly the lever that points a `cc` at a V10 toolchain instead. It was
built for a different reason and works unchanged.

Three passes still have no binary and must be built from source, which is B1d
below:

- **`ld`** — `cmd/ld.c`, 1,946 lines, "string table version for VAX", complete.
  The plan says *"No system linker is present under `cmd/`"* and *"the only
  `ld` source in the tree is `630/src/630ld.c`"*. Both are wrong; it was
  missed because `cmd/ld.c` is a loose file rather than a `cmd/ld/` directory.
- **`cpp`** — `cmd/cpp/cpp.c`.
- **`c2`** — `cmd/c2/`, four files, the peephole optimiser.

All three need only headers V8 already has. Every `#include` across `ld.c`,
`as/` and `c2/` — `stdio.h`, `ctype.h`, `signal.h`, `sys/types.h`,
`sys/stat.h`, `ar.h`, `a.out.h`, **`pagsiz.h`**, **`ranlib.h`** — is present
in `v8/usr/include`, including the two that looked least likely.

### The two failures on the way, both instructive

**`cpp.c: 14: Can't find include file libc.h`** — and the reason it cost a
whole boot is that a host-side scan had already declared every header
available. The scan matched `#include`; `cpp.c` writes `# include <libc.h>`,
with a space after the `#`, which is ordinary 1970s style and appears
throughout this tree. *Scan for `^[ \t]*#[ \t]*include`, never `#include`.*

V10's `/usr/include` is not in the source tarball, so `r70include.tar` came
down from TUHS and is now imported as `work/v10/include` (349 headers). But
only **one** of them is used: `libc.h`, copied to a directory of its own and
reached with `-I`. Pointing `-I` at the whole r70 tree is a bigger decision
than it looks, because these three passes link against **V8's** libc and
V10's headers do not all describe it — V10's `stdio.h` includes a `<tmpnam.h>`
V8 has never had, and its `sys/types.h` drops the `major()`/`minor()` macros.
That is exactly the r70-vs-1995 skew the plan predicted, it is B2's problem,
and folding it in here would have confused two questions.

Checked before relying on the one header: `libc.h` is 36 lines of `extern`
declarations and a single `#define`, with no struct layouts at all, and V8's
and V10's `struct _iobuf` are byte-identical, as are `ranlib.h`, `pagsiz.h`
and `ctype.h`. `a.out.h` differs by one bit-field name in the relocation
record — V8 spells `r_addsyl:1, :3` where V10 has `:4` — so the **width is the
same** and the two systems' object files agree on layout. `ar.h` differs only
by V10 adding `SAR_HDR`.

**`sh :yyfix` is deliberately not run.** `cpp`'s mkfile runs yacc, then
extracts the parser tables into a `rodata.c` and post-processes the assembly
with `:rofix` to move them into `.text`. That is a 1983 memory optimisation;
the tables are read-only either way. We compile yacc's output as it comes and
the cost is a few KB of data segment. Logged because someone will find
`:yyfix` in the tree and wonder why nothing calls it.

### The mid-size command is the linker

`ld.c` — 1,946 lines — compiled by V10's own compiler, and the resulting
`ld10` then linked `hello` again. The two `hello`s are worth comparing
precisely, because it says how far the agreement goes:

| | `hello` (linked by `ld`) | `hello2` (linked by `ld10`) |
|---|---|---|
| magic / text / data / bss | 0413 / 12288 / 6144 / 7628 | identical |
| symbol table size | 6324 | identical |
| text+data, bytes 32–18464 | — | **byte-identical** |
| whole file | 28,019 B | 28,019 B, **one byte different** |

That one byte is at 19512, inside the compiler's own `.stabs` record, and it
is `6a81cb7a` against `6a81cb7c` — a `time_t` two seconds apart. So the
difference is not between the linkers at all; it is that `hello.c` was
compiled twice. **The two linkers produced identical output.**

`ld` (built by V8's `cc`) is 38,674 bytes and `ld10` (built by V10's) is
51,978. Different compilers on the same source, so no byte comparison is
meaningful there — what is meaningful is that both link a working program,
and that the second was produced by the first's own toolchain.

## The golden drifted, and the rule that should have stopped it was only a rule

Running `net-selftest` to check the `v8_halt` change moved the golden's hash
from `8ccbf05614e8` to `396f994339f8`.

`net-selftest.sh` boots `rp07new` — the golden — **in place**. So do
`netfs-latency.sh` and `boot-newdisk.sh`. CLAUDE.md has carried the rule since
Track S — *run every guest harness against a CLONE, never the golden; booting
mounts, and mounting rewrites the superblock* — and net-selftest's own header
claimed the opposite of what it did: *"a pass leaves the disk exactly as it
found it."*

**Nothing was damaged, and that is what makes it dangerous.** The run halted
cleanly, all thirteen assertions passed, the exit status was 0, and the
resulting filesystem is perfectly consistent. It simply is not the artefact in
git any more. The only thing that noticed was `tools/app-check.sh` — which is
precisely why `image/ipnx-v8-rp07.img.xz` is committed. `tools/image-pack.py
unpack` put it back in eight seconds, hash-verified.

The rule now lives in `tools/v8clone.sh` and all three harnesses source it,
because a rule written in a document is not a rule that holds. The new V10
harnesses had it right from the start — which is not virtue, only recency.

Two things fell out of the repair:

- **`app-check.sh` let weak evidence veto strong evidence.** Its cheap check
  is size+mtime; `--full` adds a sha256. But restoring the golden writes
  byte-identical content with a *new* mtime, and the mtime check `continue`d
  before the hash was ever consulted — so it reported "bundled image is not the
  current golden" about a bundle whose contents provably were. Under `--full`
  the hash is now the authority and the proxy cannot overrule it.
- The proper repair was still a **rebuild**, not a silenced check: the chain is
  golden → bundle → what launches, and re-copying the restored image through it
  is what makes both paths pass honestly.

## Also fixed

`v8_halt` in `tools/v8drive.exp` sent `^E` after matching `Infinite loop`. But
that string is SIMH's own *stop* message: the CPU is already halted and scp is
already at `sim>`, so the byte landed at the head of the command line, the
next line arrived as `\005quit`, and the harness then waited out the full
240-second timeout for an eof that could not come. Four minutes at the end of
every run that halts, in every harness that sources the file, entirely after
the work had finished and passed — which is why it survived the N track and
all of Track S unnoticed.

## Replanning B2–B5, and what that turned up

Track B was written against the source-only assumption throughout, so the
remaining phases were re-planned rather than re-worded
([roadmap.md](../roadmap.md)). Four measurements came out of it, each of which
changes a phase:

**46 of ~283 command source units have a linked binary — and the boot path has
none of them.** `sh`, `sed`, `ls`, `ps`, `make`, `cpio`, `cron`, `diff`, `pr`,
`sum`, `test`, `units`, `uucp` are all prebuilt; `init`, `getty`, `login`,
`mount`, `umount`, `mkfs`, `fsck`, `sync`, `cat`, `cp`, `mv`, `rm`, `mkdir`,
`echo`, `date`, `stty` are **not**. That is not random: these are developers'
working directories, so what survives is whatever was last compiled *in place*,
and the boot path gets *installed* elsewhere. So the prebuilt set is an
**oracle, not a shortcut** — every command that has a 1995 binary is a check on
the one we build, and B3 is blocked on a list that has to be built regardless.

**The machine we already emulate is the right target.** `lsys/io` carries
`hp.c` (Massbus RP), `dz.c` (DZ11) and **`ni1010a.c`** — an Interlan driver, for
the card N2 modelled for SIMH. So `libsimh/patches/pdp11_il.c`, written for V8,
may serve V10 unchanged. Not assumed: V8's driver is `ill.c` and V10's carries
an **A** suffix, so confirming they are the same card is a B3 task rather than
a footnote.

**`star` is the 780, and `alice.m` is a real one.** `md/machstar.c`,
`consstar.c`, `nexstar.c`, `ubastar.c` and `ml/trapstar.s` are the VAX-11/780
family; `astro/alice.m` declares `ms780`, `dw780` and `mba`. The machine
configurations are named after comets and asteroids — `alice`, `arend`,
`bowell`, `coma`, `crab`, `encke`, `pipe`, `west`, `wild` — plus `research`,
the main CSRC machine, and **`r70`**, which is where `r70include.tar` came from.

**There are two kernel trees and they are not the same.** `sys/` (756 files)
and `lsys/` (763) share 522 files of which **131 differ**, and they carry
different sets of machine configurations — 10 against 17. Which one is the
kernel has to be settled before anything is compiled, not discovered halfway
through, so it is now B3.1 rather than an assumption inside B3.

## `ni1010a.c` vs `ill.c` — should V10's driver replace V8's?

Asked because V10 turning out to have an Interlan driver raises the obvious
question. **No** — but reading it was worth more than porting it would have
been.

They are the same driver eight years apart: V8's `ill.c` is 647 lines, V10's
`ni1010a.c` is 604, and the hardware interface is **identical** — the same
three registers (`il_csr`, `il_bar`, `il_bcr`) and the same commands
(`ILC_RESET`, `ILC_STAT`, `ILC_ONLINE`, `ILC_RCV`, `ILC_XMIT`, `ILC_LDXMIT`,
with `IL_EUA`/`IL_CIE`/`IL_RIE`/`IL_CDONE`/`IL_STATUS`). The body has been
substantially rewritten (514 lines added, 557 removed).

**Why not to port it into V8:**

- It is written against V10 kernel interfaces V8 does not have — `ubmalloc`,
  `ubmaddr`, `ubmfree`, `ubadrptr`, `ubmblk` for the UNIBUS map where V8 has
  `uballoc`/`ubarelse` and a hand-rolled `iladdr()`; `tsleep`/`TS_OK`;
  `stiocom`/`stiodata`/`STIOCHDR` for stream ioctls; `badaddr`; and
  `conf.h`-driven autoconfiguration (`iladdr[dev]`) instead of V8's
  `uba_device`/`ilinfo[]`. Porting means rewriting it against V8's interfaces,
  at which point it is no longer V10's driver — it is a third driver nobody
  has ever run.
- V8's networking works, is proven by `tools/net-selftest.sh`, and ships.
- **It would violate the two-goldens rule.** V8's golden is the shipped Eighth
  Edition; V10 must be built beside it, not into it.

**What reading it was worth.** V10's driver is *independent evidence about the
same hardware*, and our SIMH model was written against V8 alone.

- **The chaining rule is stated outright**, where V8 only implied it. V8 has
  the cryptic `if((bp->wptr - bp->rptr) % 8) /* not chaining */`; V10 has

      #define MKCHAIN(l)  ((l)&~07)     /* force length to allow rbuf chaining */
      #define MKTRUNC(l)  (MKCHAIN(l)-2)/* force to disallow */

  A byte count that is a multiple of 8 means *chain to the next buffer*. That
  is exactly what `il_rxpump()` was written to honour after N6 — corroborated
  now from a second source rather than inferred from one.
- **V8 polls where V10 sleeps.** `ilcdone()` spins on `IL_CDONE` up to 200,000
  times; `ilincmd()` sets `IL_CIE` on *every* command and `tsleep`s until the
  interrupt. V10 also sets `IL_CIE` on `ILC_RCV`, which V8 never does. Our
  model raises the command interrupt from the common tail of the dispatch, so
  it should be fine — but nothing has ever tested it, because V8 never asks.
- **Our receive ring is sized for V8's habits.** `IL_RXQ` is 8, with a comment
  saying "`ill.c` keeps `ILOUTSTANDING == 1` of these in flight, so overflowing
  the ring means we have a bug". V10 caps at `MAXRBUFS` 16 and queues until
  `rbytes >= ILRBYTES` (`ETHERMAXTU*2`) — about 3 buffers at `ILRSIZE` 1024,
  more when `allocb` returns smaller blocks. The comment encodes a V8-only
  assumption; the ring wants to be 16.

### The hardening, and what it cost to check

`libsimh/patches/pdp11_il.c` now names **two** conformance specifications and
sizes itself against both.

- `IL_RXQ` is `IL_MAXRBUFS` = **16**, not 8, with a compile-time assert that it
  covers both drivers' maxima. This was the one real bug: ni1010a.c never
  checks the status of `ILC_RCV`, having already done `is->rbufs++`,
  `is->rbytes += len` and linked the block before issuing the command — so a
  rejected buffer leaves driver and controller permanently disagreeing about
  which buffer a frame's next fragment belongs in. Not a dropped packet; a
  receive path that quietly stops making sense.
- Ring-full is now `sim_printf` once per attach, not a `sim_debug` nobody sees
  unless they already suspected the problem.
- The header records where V8 and V10 differ in *habit* — polling versus
  sleeping for command completion, one outstanding buffer versus sixteen,
  `MKCHAIN` stating the rule V8 only implies — because those habits were what
  the model had silently encoded as rules.

**Regression: `net-selftest` 3/3 paths, `netfs-latency` clean, golden
unchanged at `8ccbf05614e8`.** Both simulators rebuilt: the xcframework and
the desktop `vax780`, which matters more than it sounds — the desktop binary
was four days stale, so testing before rebuilding it would have exercised the
*old* model and passed for the wrong reason.

**And the benchmark turned out not to be one.** `netfs-latency.sh` reported
50 s where CLAUDE.md claimed 2 s for the same work, which looked like a 25×
regression. It is not. Five runs of the identical five-pass workload:

	committed model   32 s   47 s   49 s
	hardened model    50 s   60 s

The distributions overlap, the baseline's own spread is wider than the gap
between the groups, and a ring-size constant has no mechanism to slow a driver
that queues one buffer. So: **no measurable difference, and a harness that
could not detect one below about 2×.** The documented "530 file reads in 2 s,
~265 files/s" is withdrawn — it does not reproduce on an unmodified model, and
was almost certainly a one-pass timing written up as the five-pass one, which
is the exact error the surrounding paragraph warns against.

Worth stating plainly because it nearly went the other way: the first instinct
on seeing 50-vs-2 was that the change had broken something. The A/B took four
extra runs and half an hour, and the alternative was either reverting a correct
fix or shipping it with an unexplained 25× hanging over it.

Both driver-habit findings are B3.3 in the roadmap, with a conformance-test
item beside them — because they were found by *reading*, and what finally
settles them is a harness that drives the model the way V10 does rather than
the way V8 happens to.

One more r70 skew in passing: `ni1010a.c` uses `ETHERMAXTU`, and r70's
`sys/ethernet.h` does not define it. The 1995 source and the 1997 headers
disagree, exactly as the plan warned.

## Open

- **The r70 skew is now the live problem**, exactly where the plan said it
  would be. V10's `stdio.h` wants a `tmpnam.h`; its `sys/types.h` drops
  `major()`/`minor()`. B2 has to decide, header by header, which tree wins —
  and the answer will not be uniform, because a V10 userland compiled against
  V10 headers still has to call a V8 kernel until B3 replaces it.
- Whether V8's `exec` can page a text segment directly off a netfs mount is
  untested and deliberately so — both harnesses copy binaries to `/usr/tmp`
  first, to keep that question out of these.
- **Neither harness uses `make`.** V10 builds with `mk`, and its `mkfile`s
  assume a source directory you can write to; the sources are copied to local
  disk and compiled with explicit `cc` lines instead. That is fine for seven
  files and will not scale to a userland — B2 needs either `cmd/mk` built (it
  is in the tree, with a prebuilt binary) or a generated makefile pass like
  `v8/mk/mkdep.py`.
- The V8-cc-built `cpp`, `c2` and `ld` are in `work/v10tc/`, but nothing yet
  *keeps* a toolchain: every run rebuilds it from scratch on a fresh clone,
  which takes about six minutes and is the honest default while the recipe is
  still changing. When B2 starts iterating, the pass directory should be
  staged onto a disk image once.

## B2.0 — the boot path compiles, and the header question answers itself

The section above ends by asking whether B2 should build `cmd/mk` or write a
generated-makefile pass. Both halves of that question turned out to rest on a
claim nobody had checked, so this went the other way round: measure first,
mechanise second, which is the discipline that won B1.

### The claim that was wrong: "V10 builds with `mk`"

It does not, or not only. Counted across the tree:

	mkfile 205    Makefile 153    makefile 209    *.mk 78

Mixed, with `make` slightly ahead — and `cmd/make/make` is a prebuilt 0413
VAX executable, so if a Makefile is the thing to run, the thing to run it
with is already in the tarball.

But the number that decides the phase is a different one. **The boot path has
no build file of any kind.** `init`, `getty`, `login`, `mount`, `umount`,
`mkfs`, `fsck`, `icheck`, `sync`, `date`, `stty`, `cat`, `mv`, `rm`, `mkdir`
and `echo` are all loose `.c` files at `cmd/` top level, and `cmd/` has no
makefile or mkfile to build them with. Only `cp` and `sh` have directories.

**And there is no world build.** One candidate exists, `src/makefile`, sitting
exactly where a world build would live — 435 bytes, and it builds `fshare`, a
Datakit file-sharing daemon. Litter from someone's working directory, like the
`core` files and the eighteen stray `a.out`s.

So V10's tree is the same shape as V8's, eight years apart:

	              directories   loose .c   build file at cmd/ top
	V8  cmd/          120         168             NONE
	V10 cmd/          171         207             NONE

Which settles B2.1 by measurement rather than by preference: `v8/mk/mkdep.py`
was written for precisely this shape, and the part of it that is heavily
V8-specific — the `STAGE1` table, fifteen entries transcribing the tape's own
makefiles — is the toolchain bootstrap that V10 does not need at all.

### The probe: `tools/v10-bootpath.sh`

Seventeen programs, built twice: once against V8's `/usr/include`, once with
r70's tree ahead of it. Both configurations are defensible and that is why
both were run — a V10 userland compiled against V10 headers still calls a V8
kernel until B3 replaces it.

**35/46 assertions, and the shape of the result is the result:**

	                      V8 hdrs   r70 hdrs
	built                    10        15
	of seventeen

Fifteen of seventeen build against r70. Every one of the five that are safe to
execute on the machine that built them — `sync`, `date`, `cat`, `mkdir`,
`echo` — then ran.

The five that fail on V8 headers and succeed on r70 fail for one reason, and
it is not subtle: `sys/ttyio.h`, `sys/filio.h` and `libc.h` do not exist in V8
at all. `init`, `getty`, `login` and `stty` want the first of those.

### The tty interface is a header change far more than a kernel change

This was the thing most likely to sink B2, and it did not. V8 drives ttys
through `sgtty.h`; V10 through `sys/ttyio.h`, which V8 has never had. But the
ioctls inside line up exactly:

- every `TIOC*` V10 shares with V8 has the same `(('t'<<8)|N)` number
- V10 adds exactly two, `TIOCGDEV` (23) and `TIOCSDEV` (24), and V8 leaves
  both slots free — so they were added, not repurposed
- `struct sgttyb` is unchanged in layout; only its comments changed, marking
  `sg_ispeed`/`sg_ospeed` as "no longer set/returned by kernel"

V10 moved line speed out of `sgttyb` into a separate `ttydevb` reached by the
two new ioctls. That is the whole of the difference.

### The two that did not build, and what each one is

**`mv` builds against V8 headers and fails against r70** — `"mv.c":274:ROOTINO
undefined`. `ROOTINO` is defined in `sys/param.h` in both editions, and mv.c
includes `sys/param.h` in neither. It arrives transitively: **V8's
`sys/types.h` includes `sys/param.h` and r70's does not.**

The first reading of that was that r70 had dropped an include — a 1997
reconstruction losing a line from a 1995 header, which is exactly the skew
this phase expects. **That reading was wrong, and checking it took one
command.** The V10 tarball carries its own 1995 copy of the header in the
kernel tree, and

	src/sys/sys/types.h  ==  include/sys/types.h     byte-identical

So the reconstruction is faithful and V10's `sys/types.h` genuinely does not
include `param.h`. The defect is in **`mv.c`**: it uses `ROOTINO` and includes
nothing that defines it. That it has no prebuilt binary is consistent — it is
one of the 237 command units nobody had compiled in place when the tape was
cut.

Worth keeping as a method rather than as a fact: **the tarball contains its
own control for every r70 question.** `sys/` and `lsys/` ship 1995 copies of
the headers r70 reconstructs in 1997, so "is this skew or is this the
source?" is a `cmp`, never a judgement. Ask it before writing down an
inference — this one was plausible, published, and backwards.

**`fsck` fails both ways** — `fsck.c: 22: Can't find include file stat.h`. A
bare `<stat.h>`, and no bare `stat.h` exists in either tree; `sys/stat.h`
does. fsck was built somewhere with the `sys` directory on its include path.
One `-I` reconciles it, and it is the first entry for B2.2's patch log.

(Both configurations also print `BITFS redefined` from `sys/param.h`, because
fsck.c opens with `#define BITFS(x) (1)` before including it. A warning in
both, fatal in neither.)

### Compiling is not running: `tools/v10-syscalls.py`

Fifteen programs building says nothing about whether they *work* on a V8
kernel, and the two claims are separated by exactly one table. So the table
was diffed properly — **112 of 128 slots hold the same call at the same
index**, refining B1's approximate 111/129.

Six slots are filled in V10 and `nosys` in V8, which is the only genuinely
fatal shape: the program traps, the kernel has nothing there, and the failure
arrives as a bare errno naming nothing.

	 26  fmount        50  funmount      56  setruid
	 67  getlogname    74  setgroups     75  getgroups

Scanning the boot path for callers gives **exactly two**:

	mount    fmount
	umount   funmount

V10 mounts with `fmount(2)` at slot 26 and unmounts with `funmount(2)` at slot
50; V8 mounts with `fsmount` at 21 and `gmount` at 49, and has `nosys` at 26
and 50. Both V10 commands therefore compile, link, and cannot run until there
is a V10 kernel under them — which is not a problem, because those are the two
programs that only ever need to work on that kernel. V8's own `mount` is what
builds V10.

**Nothing else in the boot path names a call V8 lacks.**

One trap in writing that tool, recorded because it produced a plausible wrong
answer rather than an error: both editions number the upper half of the table
`64 +9` rather than `73`, since the author wrote the offset from where the
file is included. A regex understanding only a bare number reads a 128-entry
table as a 64-entry one — and then reports a clean 64/64 agreement, which
looks exactly like a result. The tool now refuses to run on a short parse.

### What this changes

- **B2.1 is settled**: reuse `mkdep.py`, because V10's tree has the shape it
  was written for and no world build of its own.
- **B2.2 is smaller than feared.** The header question is not "which tree" but
  a short list of reconciliations: r70 first, V8 filling the gaps, plus a
  `types.h` that includes `param.h` and a `stat.h` shim. Each one a logged
  patch, as planned.
- **B2.4 is nearly done before it started.** Fifteen of the seventeen already
  build; `fsck` needs an include path and `mv` needs the `types.h` fix.
- **B3 inherits a smaller question.** `mount` and `umount` are the only two
  boot-path programs whose correctness cannot be tested until the V10 kernel
  runs.

Also settled in passing, for B3.1: `lsys/os/sysent.c` and `sys/os/sysent.c`
are **byte-identical**, so the choice between the two kernel trees does not
change the system-call interface and can be made on other grounds.
