# 2026-08-19 — rung 8 is answered from the tape, and K14's partition was the bug

## Rung 8: `mux` from a 5620 on V10 — the tape names the compiler and ships none of it

Rung 8 has been carried as "blocked on an authenticity decision". It is not a
decision; it is a **measurement**, and the tape makes it in four independent
places. Nothing here needed a simulator.

### The terminal side cannot be built, and the tape says why three times

`src/history/ix/src/jerq/mux/term/makefile` is `muxterm`'s own build:

	CC = 3cc
	AS = 3as
	muxterm: ...
		3ld -o muxterm map pl.o -L$(JERQ)/lib \
			$(OBJS) frame/frame.a \
			-llayer -lj -lsys -lj -lc proctab.o
		3nm muxterm > nm.out

`src/man/man9/3cc.9` says what those are, verbatim:

	3cc, 3as, 3ar, 3ld, 3nm, 3size, 3strip, cprs \- MAC-32 C compiler
	...
	3cc is the C compiler for the MAC-32 microprocessor in the
	Teletype DMD-5620 terminal.

**Not one of those eight binaries is on the tape, and neither is source for any
of them.** The man page is the only survivor — searched by name across all
25,682 files and by every makefile that references them. The link line's
libraries are missing too: WE32100 `libj.a`, `liblayer.a`, `libsys`, `libc`
under `/usr/jerq/lib` exist nowhere.

The second route is `src/630/`, the AT&T 630 MTG tree, and it fails the same
way one layer up: `src/630/makefile` line 67 is `DMDCC=src/dmdcc`, and that
directory names a prerequisite of its own `all` target —

	all:	v9support $(DMDCC) $(MC68SGS) $(COREPRODUCTS)

— while `src/630/src/dmdcc` **does not exist**.

### And there is no prebuilt 5620 binary to fall back on

Two things were checked rather than assumed:

- **The V10 golden has no `/usr/jerq` at all.** K10.2's own transcript shows the
  harness creating it (`# mkdir /usr/jerq; mkdir /usr/jerq/include`), so there is
  no `muxterm`, no `jim`, no 5620 userland on the disk. This is unlike V8, whose
  golden ships the whole `/usr/jerq/bin` and `/usr/jerq/mbin`.
- **The one prebuilt WE32100 binary is the wrong terminal.**
  `src/630/src/muxterm` is 218,450 bytes of COFF with `f_magic` **0560** — a
  WE32100 magic, header written little-endian by VAX tools — but it is the
  **630's**, not the 5620's, and `dmd_core` emulates a 5620 running `lsys.8;7;3`.
  For contrast `blit/lib/muxterm` is magic **0407**, the 68000 Blit's, and
  `blit/Road.map` says so outright: *"This directory contains programs to run the
  Blit, the 256Kbyte 68000-based research terminal. /usr/jerq has the DMD-5620
  code"*. The naming trap, stated by Bell Labs in its own road map.

### `mux` is not in V10's live source tree at all — and that reframes the rung

`src/cmd/` has **no** jerq, mux, blit, 5620 or dmd directory. Every `mux.c` on
the tape is somewhere else:

	blit/src/mux/mux.c                        the 68000 Blit's
	src/630/src/mux.c                         the 630's
	src/history/ix/src/jerq/mux/mux.c         the NINTH EDITION's (ix = 9)

So "mux on V10" was never a V10 source-restoration target. On a real V10 machine
the 5620 software arrived as a **separate 5620 distribution tape** installed into
`/usr/jerq` — which is exactly the shape of what V8's golden has and V10's has
not. The surviving V10 copy of the 5620 software is an archive under
`src/history/`, kept for reference, not built by anything.

### The host side IS buildable, so the deviation is exactly one binary

`src/history/ix/src/jerq/mux/mux.c` is 1,144 lines of ordinary VAX C. Its mkfile
names `$CC`, not `3cc`, and links `mux` out of a seven-member `lib.a`
(`32ld.o mux.o pcheck.o pinit.o precv.o psend.o ptimeout.o`). Its includes are
V10-era and all present: `sys/ttyio.h`, `sys/filio.h`, `sys/pex.h`, `libc.h`,
`jioctl.h`, plus `/usr/jerq/include`, which K10.2 already installs.

So the split is clean: **host half buildable from the tape, terminal half
impossible from the tape.** The only WE32100 5620 `muxterm` this project
possesses is V8's — and this project already builds it, widens it
(`muxterm.w`, 1152 px) and drives it end to end.

That is a smaller deviation than it sounds, because `muxterm` runs on **the
terminal**, a different machine from the one being restored, whose firmware
(`8;7;3`) is already AT&T's rather than V10's. A 5620 was an appliance loaded by
whatever host it was plugged into.

### Would V8's terminal talk to a V10 host? The headers answer, and it is ONE constant

The three protocol headers exist on both sides, so the wire format is a `diff`
rather than a judgement — `v8/jerq/src/mux/proto/` against
`work/v10/src/history/ix/src/jerq/mux/proto/`:

	packets.h    differs only in trailing annotations on #else/#endif
	pconfig.h    adds Pxfunc(), gated on #ifndef Blit
	pstats.h     counters only
	proto.h      the real one -- see below

**`packets.h` is substantively identical**: every difference is `#else	XT`
against `#else`, the old habit of annotating a directive with its macro.
**`pconfig.h`'s difference is behind `#ifndef Blit`**, and muxterm's own makefile
compiles with `-DBlit` (`CFLAGS = -gJDMUXTERM -I. -I$(PDIR) -DBlit`), which
selects the same shape V8 uses.

`proto.h` replaced a bitfield struct with masks — and **the byte is the same**:

	bits   V8, `#ifdef vax' bitfields      V10 macros
	0-1    seq     :SBITS                  P_seq(b)     ((b) & (SEQMOD-1))
	2-5    channel :CBITS                  P_channel(b) (((b)>>SBITS) & (MAXPCHAN-1))
	6      cntl    :1                      P_CNTL       0x40
	7      ptyp    :1                      P_PTYPE      0x80

V8 needed two layouts (`#ifdef vax` and `#ifdef Blit`) because bitfield order
differs between a VAX and an m32; V10 wrote it portably instead. Same bytes.

**One wire-visible change survives, and the tape annotates it itself:**

	/* was 64 */
	#define	MAXPKTDSIZE	(124 * sizeof(Pbyte))	/* Maximum data part size */

And it is **never negotiated** — `proto.h:38` sizes the receive buffer statically
(`Pbyte data[MAXPKTDSIZE]`), `precv.c:89` *rejects* anything larger
(`if ( Scount > MAXPKTDSIZE )`), and `psend.c`'s header comment is
*"Assumes count <= MAXPKTDSIZE"*. So a 124-byte host against a 64-byte terminal
fails **cleanly** rather than corrupting, and matching the two is necessary and
sufficient.

Since we build the host from source, the fix is one line in the host, in the
direction the tape's own comment records: build V10's `mux` with `MAXPKTDSIZE`
at **64**, the value that comment says it was. That is restoring an earlier
state of the tape rather than inventing a value.

**Rung 8's status, then**: not blocked on taste. The terminal-side compiler is
absent from the tape and no substitute for it exists, so a fully-authentic 5620
`muxterm` cannot be produced at all — that is a property of what survived, like
the 1989 `libc` compiler. What *is* reachable, and what the evidence supports, is
V10's own host-side `mux` built from the tape, driving the 5620 `muxterm` this
project already has, with one measured constant matched between them.

## K14: the partition was the bug, and the swap overlap is why `h` was wrong

K14's third failure was

	unix
	mem = 6062080
	panic: iinit mount

read as a root-partition mismatch and fixed by rooting the kernel on partition
`h`. **That fix was wrong in the right direction.** `lsys/io/ra.c`'s `ra_sizes[]`:

	a   10240 blocks at 0        root
	b   20480 blocks at 10240    SWAP, and `dump' shares it
	c  249848 blocks at 30720    /usr
	h    HUGE blocks at 0        the whole drive

A filesystem on `h` **contains partition `b`**, so `ipnx780.m`'s
`swap ra 01 20480` writes swap through blocks 10240..30720 of a live filesystem.
The disk boots and corrupts itself later, which is the worst available outcome.

The panic itself is the clamp working exactly as written. `ra.c` computes
`limit = min(radsize - blkoff, nblocks)`, and K11 established that V10 puts the
free-block bitmap in the **last** blocks of a large filesystem — so mounting a
111,384-block filesystem through partition `a` reads past 10,240, gets `ENOSPC`,
sets `u.u_error`, and `iinit` panics at `lsys/os/main.c:170`.

**So the disk moved and the kernel went back to alice's value.** `alice.m` and
`seki.m` both say `root regfs ra 0100`; a whole-drive root was ours alone, and
building the disk the way V10 builds disks needs no patch at all — which is what
the authenticity rule asks for.

### And then `ra_sizes[]` turned out to be in SECTORS, which cost the next run

The first run of the corrected harness asked for **10,240 blocks** of partition
`a`, and `nblocks` in `ra_sizes[]` is **512-byte sectors** — so it asked for eight
times the partition. `mkbitfs` left `s_fsize` at 0, the mount failed, and the copy
and boot failed behind it: 6/12. **The guest never said so; the host did**, which
is the whole argument for `tools/v10-free.py`:

	v10-free: s_fsize reads 0, which is not a size partition a can hold (max 1280)

This is the V8 RP06 trap on a different disk, and CLAUDE.md has carried the
warning for V8 all along — *"RP06 partition `a` is 15,884 **sectors**, not
blocks"* — while `v10-free.py` carried the conversion in a comment on the very
table being misread. Converted (÷8) it explains the golden exactly:

	part  sectors  offset   4K blocks       MB
	a      10240        0       1280       5.0   root; the golden's root IS 1280
	b      20480    10240       2560      10.0   swap + dump
	c     249848    30720      31231     122.0   /usr; the golden uses 30752
	h     891072        0     111384     435.1   the whole drive

Two Bell Labs numbers fall straight out of it: **the golden's root filesystem is
partition `a` to the block**, and **its `/usr` is 30,752 = MAXSMALL exactly**.
Both are now copied rather than invented.

### Which forces two filesystems — the layout V10 itself uses

	partition a (root)   1,280 blocks    5.0 MB
	the boot-path copy                   6.4 MB   <- does not fit

And root cannot move. `lsys/boot/README`: *"/unix must be in the filesystem
beginning at the front of the boot device"*, and `star/uda.s` carries no partition
offset — so root is the filesystem at **sector 0**, which is `a` or `h`, and `h`
is the one that overlaps swap. So the disk gets root on `a`, swap on `b` and
`/usr` on `c`, mounted by the `/etc/rc` the golden already ships. `/lib` becomes
`/usr/lib` on the copy: it is the compiler's (libc.a and the three passes) and
nothing in a boot opens it, whereas `/etc/init`, `/etc/rc`, `/etc/getty`,
`/bin/sh` and `/dev` are what reach a login prompt.

**One deviation fewer than the last three runs had**: the golden's `/etc/rc` is
now carried across *unedited*, and the assertion that used to require the `ra0c`
mount line be stripped now requires it to be present.

### CORRECTION: the 6.4 MB figure was wrong, and the reason for two filesystems is not size

The size probe added above measured the boot-path content directly, and it is
**2.1 MB, not 6.4 MB**:

	SZ bin      833,811
	SZ etc      526,152
	SZ lib      631,774
	SZ unix     228,310
	            ---------
	            2,220,047 bytes = 2.1 MB

The 6.4 MB came from `used = s_fsize - s_tfree` on the previous run's disk —
1626 blocks of a 111,384-block filesystem — and **that difference includes the
filesystem's own 1,024-block i-list**, which is a property of how big the
filesystem is, not of what was copied into it. Data blocks were 1626 − 1024 =
**602, or 2.5 MB**, which agrees with the probe once per-file rounding to 4K
blocks is allowed for. The same arithmetic on the golden is consistent: root
1280 − 485 free − 19 i-list = 776 blocks (3.0 MB), /usr 30752 − 28008 − 473 =
2271 blocks (8.9 MB).

So a single root on partition `a` — 1,280 blocks, ~1,229 usable after its own
51-block i-list, **4.8 MB** — would have held it. **The justification written
into the commit and into CLAUDE.md was therefore wrong**, and it is worth
separating the two claims it ran together:

- **Wrong**: "there must be two filesystems because 6.4 MB does not fit in 5 MB."
- **Right, and unaffected**: root on `a`, swap on `b`, `/usr` on `c` is the layout
  V10 itself uses — the golden's root *is* partition `a` to the block and its
  `/usr` *is* MAXSMALL exactly — so it needs no kernel patch, where a whole-drive
  root needs `root regfs ra 0107` and then swaps over its own data blocks. That
  argument never depended on the size at all.

The layout also buys what rung 10 needs: 122 MB for `/usr` rather than 4.8 MB
total, which is the difference between a disk that boots and a disk that can hold
K10.3's 203 commands and K10.2's 26 libraries. And `/unix` at 228,310 bytes
retires a hypothesis raised on the way here — that an unstripped kernel was
eating the root filesystem. It is not: 223 KB is 56 blocks.

**A full V10 filesystem hangs rather than failing** (`alloc()` sleeps), so an
overflowing copy would burn the run's whole timeout with nothing to show. The
harness therefore reports `wc -c` sizes for `/bin`, `/etc`, `/lib`, `/dev` and
`/unix` *before* it builds anything — facts in the transcript, not assertions, so
even a hung run leaves the numbers behind.

Two things fell out of it that are gotchas in their own right, now in CLAUDE.md:

- **`/usr` on the golden is exactly 30,752 blocks, which is `MAXSMALL` to the
  block** (`BITMAP*BITCELL` = 961*32, `cmd/mkbitfs.c`). Bell Labs sized it to the
  largest filesystem an in-superblock bitmap can address — the very ceiling K11
  broke. Consequence: a 10,240-block root is *inside* MAXSMALL, so `mkbitfs`
  chooses `smallfree()` and reports **`flag=0`**. K14's host-side check asserted
  `flag=1` and would have failed on a correct disk.
- **Derive the minor, never write it down.** `64 | (unit<<3) | part` reproduces
  every value this project has measured — 64 and 66 off Bell Labs' own
  `/dev/ra0a` and `/dev/ra0c`, K11's 87 on rq2, K14's 79 on rq1 — so a computed
  minor cannot repeat K11's failure of addressing unit 1 while the disk sat on
  unit 2. The harness now computes it from `$UNIT` and `$PART` and writes neither.

The layout and the block count also stopped being stated twice: they were in
`v10-mkdisk.exp` while `v10-mkdisk.sh`'s host-side check hard-coded partition
`h` separately — the shape of fault CLAUDE.md records as *"a component list that
appears twice will disagree, silently"*. They are now defined once, in the
driver, and passed down.

## Rung 8's host half: where its headers are, so the next phase starts from facts

`mux.c` names eight headers beyond the obvious. Four are in r70's `/usr/include`
already and four are not, which is the same *system-layout* question `shares.h`,
`stdlib.h`, `float.h` and `stdarg.h` each turned out to be — the header exists on
the tape, under a path that is not `/usr/include`:

	present    sys/ttyio.h  sys/filio.h  sys/stream.h  libc.h
	absent     sys/pex.h    tty.h        sys/label.h   jioctl.h

And each absent one has exactly one sensible source:

- **`sys/pex.h` → `src/history/ix/include/sys/pex.h`.** It exists nowhere else, and
  that is *coherent* rather than awkward: `mux.c` is itself from `history/ix`, so
  the whole subsystem is the Ninth Edition's, headers included. Taking the header
  from the same tree as the source is the conservative choice, not a mixture.
- **`sys/label.h` → r70 has `include/label.h`, at top level.** So the header is
  present and only the *path* is wrong — the mirror image of `fsck.c`'s bare
  `<stat.h>` where every other command says `<sys/stat.h>`. A copy under `sys/`
  settles it without touching source.
- **`tty.h` and `jioctl.h` belong to the 5620 include tree**, which is what
  `JINCL = /usr/jerq/include` on mux's own mkfile is for — K10.2 already installs
  that tree, including our `jioctl.h` with the `JMUX` alias. So these need no
  decision at all; they need the `-I` the mkfile already carries.

Nothing here is a blocker, and none of it is a guess: `find` over all 25,682 files
returns one candidate for `pex.h` (two copies in the same tree) and one for
`tty.h`. Recorded now because the expensive part of every previous header question
was discovering that the decision had already been made somewhere else.

### The host's own reading, and the geometry matches Bell Labs' exactly

	                       root (a)        /usr (c)
	filesystem size    1280 blocks     30752 blocks
	i-list               19 blocks       473 blocks
	s_tfree             826 blocks     30115 blocks
	free BY BITMAP      826 blocks     30115 blocks   <- counted, not read
	flag                        0               0
	block 0                            475 of 512 bytes non-zero

**The i-list figures are identical to the golden's own — 19 and 473.** They follow
from the filesystem size, and we used Bell Labs' sizes, so the geometry of what V10
built here is the geometry of what Bell Labs shipped. Both free counts agree
between `s_tfree` and a bit-by-bit count of the bitmap, which are different places
in the superblock, so a disagreement would have been real news.

The data used checks out against the probe from the other direction: root 1280 −
826 − 19 = **435 blocks (1.78 MB)** against `bin` + `etc` + `unix` = 1.59 MB plus
4K per-file rounding; `/usr` 30752 − 30115 − 473 = **164 blocks (0.64 MB)** against
`/lib`'s 0.60 MB. Two independent measurements of the same copy.

### Two faults of mine on the way, both worth keeping

**I EDITED `tools/v10-mkdisk.sh` WHILE BASH WAS STILL READING IT, and it silently
skipped the verification.** CLAUDE.md has the rule — *"during a run, `docs/`,

bash is still reading are not"* — and I broke it to fix a comment. bash reads a

`ding.` is the tail of `hiding.`, the last word of line 120. The 14/14 was

**And `pwd` is absent from the V10 golden**, which the copy said in passing:

Harmless here — `cpio -pd` copied everything and `CP-ok` was written by the success

### What K14 settles, and what it does not

Settled: **the mechanism of rung 10 exists.** V10 can partition, make filesystems,
populate them and boot the result, with its source arriving over the network. What
remains for a shippable `v10.disk` is *what to copy* — K10.3's 203 commands,
K10.2's 26 libraries, stage 1's toolchain — plus `/lib` moving back to root where
the golden keeps it, and then the Swift work to carry a second machine in the app.

### Two blemishes the passing transcript exposes, neither fatal

**`/etc/mtab` is copied, so the new disk boots believing the BUILDER's mounts.**
Boot 2's `umount -a` answers over three stale lines, and `cat /etc/mtab` on the new
disk shows them:

	/usr        /dev/ra0c
	/mnt2       /dev/ra1a
	/mnt2/usr   /dev/ra1c

The last two are the builder's own mount points for the disk being built. It is
cosmetic — V10 rewrites `mtab` as things mount, and the boot reaches `login:`
regardless — but a shipped disk should not carry another machine's mount table.
`/etc/mtab` wants truncating on the copy, beside `/lib` moving back to root.

**And boot 2 has no Interlan attached, so autoconfig says so:**

	ub0: cfg28 sr5 fubar 764000
	ni1010a 0: reset failed csr 0

That is correct behaviour, not a fault: boot 2 deliberately attaches only the new
disk — no `set il enable`, no `attach il nat:` — because the point of that boot is
that the disk stands on its own. `/etc/rc` guards the network on `/dev/il0` exactly
as V8's does, so the machine comes up anyway and prints its banner. Worth knowing
so the two messages are not read as damage next time.

For the record, `mkbitfs` printed its own arithmetic, which is a third independent
witness to the geometry:

	1280 4k blocks, 17 blocks of inodes, 1088 inodes
	30752 4k blocks, 471 blocks of inodes, 30144 inodes

and both halts were clean — `death`, then `Infinite loop, PC: 80015CC9` — so
neither image was left inconsistent.

## Both blemishes fixed and verified — 14/14 again, exit 0

`/lib` is back on root where the golden keeps it, and the copied `/etc/mtab` is
truncated. **Both are confirmed by their effects rather than by the absence of a
complaint**, which is the discipline this project keeps relearning:

	                 before    after
	root free          826       664     -162 blocks
	/usr free        30115     30278     +163 blocks

`/lib` is 631,774 bytes — about 155 blocks plus per-file rounding to 4K — so the
two figures move by the same amount in opposite directions. That is `/lib` leaving
`/usr` and arriving on root, measured twice from different superblocks, rather than
inferred from a successful copy.

And boot 2, which is where the stale mount table showed:

	before   cat /etc/mtab   ->  /usr /dev/ra0c, /mnt2 /dev/ra1a, /mnt2/usr /dev/ra1c
	         umount -a       ->  three errors, two of them the BUILDER's mount points
	after    cat /etc/mtab   ->  nothing
	         umount -a       ->  nothing

Truncated rather than removed, because `mount` appends to `/etc/mtab` and it has to
exist.

So the disk V10 builds now carries the golden's own layout *and* the golden's own
directory placement, with no mount table but its own — and `tools/v10-mkdisk.sh`
reports **14/14, exit 0** with the host's independent reading agreeing on both
filesystems.

## K15 — rung 8's host half: reconnaissance, and three things it corrected

Rung 8's terminal half was settled above: `muxterm` cannot be built, because the
`3cc` family is documented and not shipped. What remains is the **host** half —
`mux` itself, 1,144 lines of plain VAX C whose mkfile names `$CC` — and this is
the reconnaissance for it. All of it is host-side, in about a second, and it
corrected the record three times before a simulator was started.

### The missing-header count was four, then five, then six

The number written up on the morning of the 19th was **four**, and it was wrong
in both directions. Two of the four are not missing at all:

	tty.h      one of the 21 in the v10blit tree v10_jerq_inc already copies
	jioctl.h   comes from our own overlay, with the JMUX alias

And the requirement is larger than a reading of the seven sources shows, because
**a direct include scan is not the requirement — the transitive closure is**:

	sys/xtproto.h   reached only through proto.h and packets.h
	sys/jlabel.h    reached only through sys/label.h

Neither is named by any `.c` file, so two rounds of reading the sources missed
both. What is actually needed, and where each comes from:

	aouthdr.h filehdr.h scnhdr.h   630/3binc      COFF, for 32ld.c
	sys/label.h sys/pex.h          history/ix     the V9 path convention
	sys/jlabel.h                   history/ix     reached via label.h

They go into `/usr/jerq/include`, **not** `/usr/include`, and that is a
measurement rather than a preference: all **44** consumers of `<sys/label.h>` and
every consumer of `<sys/pex.h>` are under `src/history/ix/`, while V10's own live
tree writes `<label.h>` unprefixed and r70 provides that at top level. So this is
the *Ninth* edition's path convention, not a gap in V10, and installing V9 headers
system-wide to build one V9 program would be the wrong trade. Nothing outside mux
is touched.

`sys/label.h` also settles in the opposite direction to the first measurement.
r70's own top-level `label.h` would serve mux's default build — every symbol it
reaches is there, the two absentees (`labEQ`, `labtoa`) being used only inside
`trace()`, which is `#define trace(a,b)` without `-DTRACING`. But **r70's
`label.h` includes `sys/jlabel.h` and r70 has no `jlabel.h` anywhere**, so V10's
copy is unusable as shipped. The ix tree carries both, so the pair comes from
there rather than mixing generations.

### `sys/xtproto.h` is a false alarm, and the tape says so in both files

	#ifdef	XT
	#ifndef	MAXPCHAN
	#include	"sys/xtproto.h"
	#endif
	#else
	   ... every definition, inline ...

Both `proto.h` and `packets.h` open exactly that way, and the mkfile's CFLAGS
never define `XT`. V8's copies are structurally identical **and V8 does ship
`jerq/include/sys/xtproto.h`** — so the header is real; it is the XT variant's,
and no V10 build of mux wants it. It is named in `MUX_UNREACHED` with that
reason rather than dropped, because a resolver that silently drops what it cannot
find is how a missing header becomes a mystery three hours into a build.

### The COFF variant was measured, not preferred

Two copies of each survive. A probe compiled against both prints identical sizes
and identical offsets for every field `32ld.c` touches:

	filehdr 40   f_magic@0  f_nscns@2  f_opthdr@32
	aouthdr 56
	scnhdr  72   s_scnptr@32  s_size@24  s_paddr@8

So correctness does not decide it and provenance does. The 5620 is a WE32100;
`630/3binc` is the BELLMAC-32/3B include tree and its `filehdr.h` carries the
`F_BM32ID`/`F_BM32MAU`/`F_BM32B` identification flags; `cmd/kasb` is a **KMC11**
assembler whose first line is `#undef vax` / `#define pdp11 1`. `32ld.c` takes no
magic number from a header at all — it defines `FBOMAGIC 0560` itself.

Neither directory goes on `-I`, only the six named files: `630/3binc` also holds
`ctype.h`, `string.h`, `memory.h` and `search.h`, and `history/ix/include` holds
V9 copies of `sys/param.h`, `sys/types.h`, `sys/stat.h`, `sys/stream.h`,
`sys/ttyio.h` and `sys/filio.h`. Putting either on the include path would silently
replace V10 headers with someone else's — the trap already recorded for
`include/CC`. **mux must see V10's kernel interface however old its source is**,
because it is a program for a V10 kernel.

### AND THE PACKET SIZE IS 124, WHICH RETRACTS THE TASK'S OWN PREMISE

This is the finding worth the most. `proto.h` reads

	/* was 64 */
	#define	MAXPKTDSIZE	(124 * sizeof(Pbyte))

and that annotation is why CLAUDE.md said building at 64 "restores the tape's own
earlier value". **It does not.** The annotation is a comment about the *source*;
the tape also ships Bell Labs' own *compiled* `lib.a` beside it, and pcc emits
uninitialised file-scope arrays as **common** symbols, where the symbol's value
*is* its size:

	124  _buf         char buf[MAXPKTDSIZE]        mux.c:57
	132  _precvpkt    struct Pktstate              = Packet 128 + state + timo
	4400 _layer
	4416 _pconvs

So the shipped artefact was built at **124**, and the annotation records a change
made *before* 1989. Building at 64 is therefore a **deviation for
interoperability**, not a restoration — and the authenticity rule allows a
deviation only when the tape cannot run as-is, which here it can. K15 builds 124
and asserts it through `sizeof(struct Packet) == 128`. Matching V8's `muxterm` at
64 is a second, separate decision, and it needs more than a constant: V10's golden
has no `/usr/jerq/bin` at all, so V8's `muxterm` binary would have to be installed
as the download payload too.

*A comment in a header is evidence about intent. An object is evidence about what
ran.*

The same objects answer a question that would otherwise have been a risk.
`pcheck.c`'s `#ifdef vax` arm is four `asm()` lines using the VAX `crc`
instruction, and `pcheck.o` carries a **64-byte `.data`** — which is `crc16t[16]`,
so that arm is the one Bell Labs compiled. On our side `asm` is in V10 ccom's
keyword table (`scan.c:862`) and V10's `as` knows `crc` at opcode `0x0b` with
exactly the four operands `pcheck.c` writes (`cmd/as/instrs:101`).

`lib.a`'s members are dated **1989-01-02** (six) and **1989-07-15** (`mux.o`) — the
working-directory pattern in miniature, the same shape as `libc.a`'s 4.1-year
spread. That is the era CLAUDE.md establishes is unreproducible: the compiler that
built it is not on the tape, and these are most likely Ninth Edition objects
besides. So a byte difference against them is the **expected** result and is
reported as a number beside the number that matters, exactly as stage 2 reports
built-versus-identical.

### Two faults caught before a boot was spent, each by a tool that exists for it

**`mux_closure()` raises where `mkgen.scan_includes()` drops.** The generator's
own resolver returns silently on an include it cannot place — documented, and
correct for its purpose — but for a component whose headers come from four
different trees that is how a build fails twenty minutes in on `Can't find include
file`. `mux_closure()` fails the *generator* instead, and it earned that on its
first run:

	mkdep: mux: cannot resolve #include sys/jlabel.h, reached via sys/label.h.

**`tools/v10-dryrun.sh` caught the oracle loop reading the wrong thing.** The
first version counted verdicts in Tcl with `regexp {CMPSAME} $expect_out(buffer)`
after `v10_run` — and `v10_run` ends in `v10_sh ":"`, whose own `expect`
overwrites `expect_out`. So it would have been reading the resynchronisation, not
the answer. The counting is the driver's now, from the log, with an **unanchored**
grep, which is stage 3's pattern and carries stage 3's reasons: the echo of the
command shares a line with the first line of output, `sort -u` because the token
appears twice, and `grep -c .` because `grep -c` prints 0 and exits 1.

One more, from the same class: the object list goes into a shell variable before
the comparison loop, because spelled out in full the typed line reached ~230
bytes and **CANBSIZ is 256** — a tty line over that is discarded silently, so one
more object would have meant the comparison never ran at all.

### A macro used before it is defined, and why that is correct here

`mux.mk` uses `$(JERQINC)` in its `INCS` line (71) and defines it eleven lines
later (81), because the include flags come from the shared `PREAMBLE` template
and the 5620 directory is appended after it. That looks like a latent bug, and
V10's own `make` says it is not. `cmd/make/misc.c`:

	210  char *subst(a,b)
	...
	242			b = subst(vbp->varval, b);

`subst` **recurses into a macro's stored value**, and `doname.c:297` calls it on
a command line at *execution* time — so definitions are stored verbatim and
expanded recursively when used, by which point the whole makefile has been read.
(Dependency lines are different: `gram.c:287` substitutes those at parse time.)

So the ordering is correct by construction rather than by luck, which is worth
knowing before "fixing" it: immediate expansion is a later invention, and no
1980s make has it.

## AND THE HOST HALF IS IX's, NOT V9's — which is a harder wall than the compiler

"The host half IS buildable" was **my** claim, made from reading `mux.c`'s
includes and its mkfile's `$CC`. It compiles. **It does not link**, and the
reason is structural rather than a missing `-l`.

Predicted host-side, before the run reached the link, by reading the undefined
externals out of Bell Labs' own `lib.a` — the same 20-line symbol dump that
answered the `<shares.h>` question. The seven objects define 98 externals between
them and leave **45** for libc, and five of those forty-five are not in V10 at
all:

	pex, unpex        V9 syscalls -- V10's lsys/sys/sysent.c has no `pex'
	unsafe            in ix/sys/os/sys5.c  -- the V9 KERNEL, not libc
	labEQ, labLE      in ix/sys/os/jlabel.c -- the V9 kernel again

Every call is unconditional and in the main path, and one of them is not
peripheral at all:

	mux.c:186    if(pex(0,-1,0)!=0) { untrusted++; unpex(0,-1); }
	mux.c:1051   int nfds = unsafe(NSELFD, &readfds, &writefds);
	mux.c:962    if(p->busy && !labEQ(&p->lab, &label)
	mux.c:1074   if(!labLE(&layer[fd].lab, &lab)) {

`mux.c:1051` is **the main event loop**. `unsafe()` is a *labelled* `select()`.

### `src/history/ix` is IX, Bell Labs' security-enhanced Ninth Edition

That is what ties it together, and the directory has been read all week as "the
Ninth Edition's archive" when it is something more specific. Beside `jerq/` in
that tree sit `cmd/integrity.c`, `cmd/downgrade.c`, `cmd/notary.c`,
`cmd/privserv/`, `cmd/setlab.c`, `cmd/getlab.c`, `cmd/nosh.c` — mandatory access
control, labels and levels. `sys/label.h`, `sys/jlabel.h` and `sys/pex.h` are IX
headers, and **44 files under `src/history/ix/` include `<sys/label.h>` while
V10's own live tree includes `<label.h>` unprefixed**.

CLAUDE.md already had the corner of this and did not follow it: *"`flabclr`, 'for
security unix', looks like a symbol from a Bell Labs variant we do not have"*. It
is IX, and this is that variant.

V10 kept **part** of the interface — `libc/sys/label.c` really does define
`fgetflab`, `fsetflab`, `getplab`, `setplab` and `nochk`, so four of mux's label
calls resolve — and dropped the rest. So the wall is not "V10 has no labels"; it
is that V10 has the *file* label calls and not IX's process-exchange, labelled
select, or label comparison.

### The 630's mux links but speaks a different protocol

`src/630/src/mux.c` is the obvious alternative and it is genuinely clean: **no
`pex`, no `unsafe`, no `labEQ`/`labLE`, no `getplab`**, and its include list is
the ix one minus `sys/label.h`, `sys/pex.h` and `libc.h` — so only `jioctl.h` and
`tty.h`, both of which `/usr/jerq/include` already carries. It would link today.

It is the wrong protocol. The 630's `proto.h` does not write a constant, it
writes a *derivation*:

	#define	MAXPKTDSIZE	MAXPKTSIZE-(PKTHDRSIZE+PKTCRCSIZE+PKTASIZE)

`PKTASIZE` is an **address** field that neither V8's protocol nor the ix one has.
So this is a later generation of the packet format, not the same format with a
different size, and it would not talk to the only 5620 `muxterm` this project
possesses. `src/630/src/` also has no `32ld.c` at all — only a `32ld.note` — so
its downloader is different too.

### What rung 8's host half therefore is

Three statements, and keeping them apart matters:

- **There is no V10 mux.** `src/cmd/` has none, so there is no authentic V10
  artefact to be faithful *to*. This is not a case where the tape can run as-is.
- **The closest surviving host-side mux that speaks V8's protocol is IX's**, and
  running it on V10 needs five IX interfaces ported. Four of the five have an
  obvious V10 answer, and all four have their evidence on the tape: `unsafe` →
  `select` (V10 has it, `libc/sys/select.s`, and it is a libc member);
  `labEQ`/`labLE` → the comparisons in `ix/sys/os/jlabel.c`; `pex`/`unpex` →
  mux *already handles failure* (`untrusted++`), so a stub that fails is
  behaviour the program is written for.
- **The 630's mux links but cannot talk to our terminal.** Choosing it would
  trade a protocol match for a link, which is the wrong way round: a program
  that links and cannot speak is no better than one that speaks and cannot link.

So the honest form of rung 8 is: terminal half **impossible** (no `3cc`); host
half **compiles, and links only with a named port of five IX interfaces**. That
is a bigger deviation than the single `MAXPKTDSIZE` constant this rung was
carrying as its only obstacle, and it is worth more than a false claim of
success.

### And the port is smaller than "port five interfaces" sounds, because IX's libc is on the tape

`src/history/ix/src/libc/` exists — 33 files — and it carries **all five**:
`labEQ.c`, `labLE.c`, `pex.c`, `unsafe.c` (plus `labMAX`, `labMIN`, `labconst`,
`label`, `labmount`, `labtoa`, `labtrans`, `pexpw`). So this is not writing
substitutes for Bell Labs' functions; it is compiling more of Bell Labs' own
source. Each was then checked against V10 rather than assumed:

	labEQ.c    17 lines of pure C on `struct label', including only
	           <sys/label.h> -- which mux.inc already installs.  Compiles on
	           V10 unchanged.  labLE.c is the same shape.

	pex.c      73 lines of C, and NOT a syscall -- it is an ioctl protocol
	           built on FIOPX from <sys/filio.h>.  V10's sys/filio.h HAS NO
	           FIOPX, so it cannot compile.  That is survivable and the
	           program says so itself:

	               if(pex(0,-1,0)!=0) { untrusted++; unpex(0,-1); }

	           mux is written to run untrusted when pex fails, so a stub that
	           fails is behaviour it already handles.

	unsafe.c   seven lines, and the whole body is
	               return syscall(64+36, n, r, w);
	           V10's lsys/os/sysent.c line 184 is
	               0, nosys,            /* 64+36 = nosys */
	           so compiling IX's version calls an EMPTY SLOT.  It fails
	           safely rather than doing something else's work -- but it fails,
	           and mux's next line is quit("unsafe failed").

So `unsafe` is the one that must be *mapped* rather than compiled, and V10 has
exactly the call to map it to: `select`, `libc/sys/select.s`, `.set select,38`,
a real libc member. The signatures differ by one argument —
`unsafe(nfd, rp, wp)` against `select(nfd, rfdset, wfdset, time)` — and IX's
`unsafe()` differs from a plain select only by label filtering
(`jl_t(u.u_procp->p_lab) & T_NOCHK`), which is precisely what a label-less V10
does not need.

**Checking the slot mattered.** Had V10 filled 100 with something else, compiling
IX's `unsafe.c` would have called that something else with select's arguments,
on every pass of mux's event loop. It is `nosys`, so the failure mode is an
error rather than a wrong syscall — but that is luck, and the check is the
reason we know it.

## The netfs round trip costs ten seconds, and that is now the binding constraint

K15 spent **fourteen minutes copying nineteen small headers**, and then its
`make` step spent a further ten walking prerequisite paths without compiling
anything. Both follow from one number, measured from netfsd's own request
counter during the run:

	30 requests in 289 s  =  9.6 s per request

Sampled twice, steady rather than degrading, and the same order of magnitude as
K14's single-file `mkbitfs` build taking twenty minutes. **The request count is
not the problem**: 165 requests for 25 distinct files is 6.6 per file, which is
reasonable, and there are no netfs-level retries — the apparent duplicates in
the trace are different names looked up in one directory, which the request
signature does not distinguish.

### "About a hundred times slower than V8" is withdrawn, and it was mine

I wrote that at the end of the previous session and repeated it here. There is
**no comparable V8 netfsd trace on disk to check it against**:
`work/netfs-run.log` is a harness log rather than a server trace, and the only
traces carrying the request counter are V10's own, at 25 and 27 requests — far
too small for a rate. The V8 figure it leaned on (9–17 files/s) comes from a
different harness and a different workload, and CLAUDE.md's own entry for that
script says it has **~50% run-to-run variance** and that an earlier number from
it was **withdrawn as unreproducible**. So the ratio was resting on a baseline
this project already distrusts.

It changes nothing that matters. Ten seconds per round trip is untenable in
absolute terms, whatever V8 does.

### Two candidates, and one command discriminates

**A — dropped frames and a TCP retransmit.** 9.6 s is the shape of a 5–6 s
initial RTO. The mechanism is in our own device model and already counted;
`libsimh/patches/pdp11_il.c:659`:

	if (il.rxq_count == 0) {          /* nowhere to put it */
	    il.lost = 1;
	    il.ierrors++;
	    sim_debug (DBG_PKT, &il_dev, "receive with no buffer, frame dropped\n");
	    return;
	    }

and V10's `ni1010a.c` posts at most **one** receive buffer at a time —
`ilrcvbufs()` returns 0 the moment `is->flags & CMDACT` — where V8's `ill.c`
supplies the next buffer from inside `ilrint()`. `il_rxpump()` was written for
V8's driver and measured against it (stage 7, 290 s → 11 s); it has never been
measured against V10's.

**But reading `il_rxpump()` weakens my own hypothesis**, and that belongs on the
record next to it. In a strict request/response protocol the guest re-posts its
buffer while handling the previous reply, and it cannot send request N+1 until it
has reply N — so a buffer should normally be posted before the next reply can
arrive. The drop window is real; whether it is reached once per request is not
established.

**B — the fast-poll window expiring into a slow clock.** `il_svc()` polls fast
for `IL_BURST` = 200 service calls after a packet and then falls back to
`sim_clock_coschedule(uptr, tmxr_poll)`. On V8 that is the calibrated 10 ms
clock, which is the entire point of the burst window. If V10's machine leaves
that clock in a different state — its config never sets `set cpu idle`, and its
kernel programs its own timers — the coschedule could land much further out.

`show il stats` separates them, because `il_show_stats()` already prints
`receive errors` and `REG IERRS` already exposes it: **on the order of the
request count means A; near zero means B.** No code change, no extra run — so it
now runs at every V10 halt, on both paths, from `v10_halt` in
`tools/v10drive.exp`. It is a property of the machine rather than of one harness.

### And an instrument that was measuring nothing

`netstat -s -p tcp` looked like a free way to count retransmits. It reported zero
retransmits, zero timeouts — and, checked one line further, **`0 packet sent`**,
on a machine passing traffic continuously. The statistics are privileged on this
macOS, so the reading was an absent instrument rather than a clean result, and
banking it would have been this project's own recurring error: a test that cannot
fail is not a test.

It could not have answered the question in any case. SLiRP terminates the guest's
TCP and opens its own socket to netfsd on the host loopback, so the leg that
matters — guest to SLiRP, across the emulated Ethernet — is invisible to host
statistics **by construction**. Only a counter inside our own device model can
see it, which is exactly what `il.ierrors` is.

### The deciding arithmetic, and it was in our own code comment all along

The V8 baseline this needed was never in `netfs-latency.sh`. It is in
`libsimh/patches/pdp11_il.c:775`, written down while explaining why the burst
window exists at all:

	"tmxr_poll rides the 10 ms system clock, which is why this measured
	 ~16 ms a request and ~30 files a minute regardless of file size."

That is the **unpatched** V8 rate, from this project's own measurement, and it
settles the question of mechanism:

	V8 unpatched       ~16 ms per request
	V10 measured      9600 ms per request        600x worse

**So V10 is far slower than V8 was before `il_rxpump()`'s fast-poll window ever
existed**, and that reorders the two candidates rather than merely ranking them:

- **Candidate B cannot be the primary cause.** Its worst case is one 10 ms clock
  tick per exchange — which is *precisely* the unpatched behaviour quoted above.
  It is 600× too small. Nothing anywhere in the polling path can produce 9.6 s.
- **Only a timeout is the right order of magnitude.** A 1980s initial RTO is
  5–6 s with backoff, and 9.6 s is that shape. So candidate A — a frame lost and
  recovered by retransmission — is the one left standing, and the drop site is
  ours and already counted.

The caveat from reading `il_rxpump()` still stands and is what makes this a
prediction rather than a conclusion: in strict request/response the guest
re-posts its buffer while handling the previous reply and cannot send request
N+1 before reply N, so the drop window may be rare rather than per-request. If
`receive errors` comes back near zero then **both** candidates are wrong and the
timeout lives somewhere else — V10's own retransmit timer, or the stream layer —
and the next step is timestamps in netfsd rather than a third guess.

Either way the instrument is already wired and costs nothing: `show il stats` at
every V10 halt.
